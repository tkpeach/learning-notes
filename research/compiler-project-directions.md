# 编译系统专项项目：选题、边界与验证设计

整理日期：2026-10-19。问题来源与技术资料沿用 2026-10-16 前的核查结果；本文没有重新确认所有仓库的版本状态，也没有实际构建、执行或测量这些候选。所有首版规格、接口和验收条件均为设计建议，示例数字不是实验结果。

本文集中维护七个项目方向，统一说明问题依据、输入输出、简单例子、实现范围、验证方法、资源门槛和能力覆盖。只保留技术资料与能力对照，不收录人员需求信息及相关链接。

## 1. 选择原则与总览

目标是做出一个独立、可运行、可复现、能解释设计取舍的小系统。已有基础为 C++、EDA 和部分信号处理；可用环境为 Mac、WSL，必要时迁移原生 Linux。具体宿主架构、内存和磁盘尚未确认，不预设 Apple silicon、CUDA 或专用板卡可用。

一个合适的项目应满足：

1. **来源成立。** 有公开系统、论文或清楚的工程需求作为依据，能说明为什么需要这种能力。
2. **范围足够。** 处理一类输入，包含多个相互影响的编译决策，最终产生可执行产物或可集成组件。
3. **边界明确。** 第一版可以排除大量语言特性、硬件和平台，不以复刻完整工业系统为目标。
4. **结果可判断。** 正确性有独立参照，效果有合理基线，不用单一漂亮案例证明普遍优势。
5. **实现由自己掌握。** 可以复用前端、基础设施和 kernel，但核心分析、变换、规划或生成逻辑应由项目实现。

实现一个已经成熟的问题也可以形成扎实成果，但应明确区分方法复现、工程实现与研究扩展。运行已有工具、移植构建脚本、增加界面，不能单独承担核心技术内容。也不必以全面超过成熟系统作为项目成立的前提。

### 1.1 七个候选

| 编号 | 方向 | 核心问题 | 最终产物 | 主要技术深度 | 相对风险 |
| --- | --- | --- | --- | --- | --- |
| A | 低延迟原生代码 JIT | 编译成本、执行速度与运行时依赖的平衡 | 受限 IR 的原生执行系统 | 模板生成、重定位、布局、ABI | 高：平台和工具链细节 |
| B | 内存预算驱动的计算图编译器 | 联合选择执行顺序、生命周期和布局 | 可验证的执行计划与 CPU 程序 | 图调度、资源约束、内存规划 | 中高：语义与集成 |
| C | 列式表达式编译执行引擎 | 融合执行收益与编译开销的平衡 | 表达式 IR 到原生函数的引擎 | 融合、空值、向量化、JIT | 中高：范围与数值语义 |
| D | 可验证寄存器分配库 | 在有限资源和指令约束下保留数据流 | 分配库、checker、小型执行后端 | 活跃分析、spill、约束、SSA 消解 | 高：正确性与算法复杂度 |
| E | 受限 RTL 编译式仿真器 | 将并行电路状态转成正确高效的软件执行 | 硬件 IR 到仿真模型的编译器 | 静态调度、状态布局、位向量、CodeGen | 中高：电路与执行语义 |
| F | 组合逻辑综合与 LUT 映射器 | 逻辑结构与目标映射的面积／深度取舍 | 组合网络到 LUT 网表的工具 | 图重写、cut、动态规划、等价验证 | 中高：强基线与映射质量 |
| G | 资源受限静态 HLS 后端 | 资源数量、算子延迟与执行周期的取舍 | 计算 DAG 到 FSM＋datapath RTL | 调度、绑定、寄存器、控制生成 | 高：软硬件联合验证 |

优先深入调查 E、A、B；如果更关注逻辑综合与映射，用 F 替换 E。D 是机器后端专项选项；C 是数据处理专项；G 是硬件调度专项。这个顺序考虑已有基础、验证闭环和首版规模，不是技术价值排行榜。

### 1.2 能力覆盖的解释

- **直接覆盖：** 自己实现的核心模块能够形成完整技术证据。
- **部分覆盖：** 只涉及相邻模块、受限子集，或者主要复用了现有基础设施。
- **未覆盖：** 不能由项目名称或依赖关系推出已经掌握。

| 方向 | 直接覆盖 | 部分覆盖 | 首版未覆盖 |
| --- | --- | --- | --- |
| A | 原生代码生成工程、重定位、执行接口、编译延迟分析 | 优化策略、指令选择思想 | 完整 LLVM target、GPU/SIMT 后端 |
| B | 图调度、生命周期、arena 规划、资源约束验证 | 张量 lowering、CPU 执行集成 | GPU 显存与通信、训练栈、多设备 |
| C | 领域 IR、融合、表达式 CodeGen、JIT 缓存 | SIMD 与批执行 | 存储、事务、分布式系统、完整 SQL |
| D | 寄存器分配、spill/reload、约束与数据流修复 | ABI、指令编码 | 完整指令选择和调度、多寄存器类 |
| E | 电路 IR 调度、状态语义、仿真模型生成 | HDL 编译与仿真运行时 | 完整 SystemVerilog、四态事件调度、UVM |
| F | 逻辑优化、LUT 映射、图算法与等价检查 | 综合流程与延迟估计 | 物理设计、标准单元全流程、签核 |
| G | 硬件调度、资源绑定、控制与 RTL 生成 | 时序建模、位宽分析 | 流水循环、存储系统、板级时序与功耗 |

## 2. A：低延迟原生代码 JIT

### 2.1 问题来源与独立价值

运行时系统希望快速开始执行，同时又希望生成高质量代码。解释器、快速基线编译器和优化编译器处于不同取舍点。Copy-and-Patch 通过离线准备机器码 stencil，在运行时拼接并修补常量、地址与跳转，减少在线生成成本。

该方法有 OOPSLA 2021 论文、PochiVM 公开参考实现，以及 CPython 实验性 JIT 中的应用。它证明问题有工程意义，但不意味着参考实现适配当前工具链，也不意味着复现后一定获得论文中的收益。

项目问题：**为受限计算 IR 实现快速原生执行系统，刻画不同编译模式的总成本，并研究一种有限的代码质量策略。**

### 2.2 一个简单例子

```text
输入程序：遍历数组 x；若 x[i] > 0，累加 3*x[i]+1；返回总和。
输入数据：x = [-2, 0, 1, 4]
输出：17

执行路径一：IR 解释器逐条解释。
执行路径二：拼接 stencil，修补常量与跳转后执行。
执行路径三：将相同语义交给 LLVM 优化后执行。
```

一次运行与反复运行的最佳方案可能不同。评价目标为 `T_total = T_compile + N × T_execute`，不是只比较预热后的函数速度。

### 2.3 第一版契约

| 项目 | 约定 |
| --- | --- |
| 编译输入 | 验证过的结构化 IR；不实现通用语言 parser |
| 数据类型 | 有符号比较与定宽整数；算术明确采用模 2^64 语义，避免依赖 C++ 有符号溢出 |
| 操作 | 常量、加减乘、比较、分支、循环、受限数组读取与返回；不含除法 |
| 内存 | 宿主提供数组与长度；首版只允许 verifier 可证明的范围内读取，例如 `0 <= i < len` 的规范循环；宿主检查指针／长度契约，无法证明安全的索引直接拒绝编译 |
| 调用接口 | 固定一种函数签名；首版不支持任意外部调用 |
| 输出 | 原生函数入口、代码大小、编译统计及可检查的反汇编 |
| 平台 | 一个实际可执行的宿主 ISA＋OS；不预先承诺跨平台 |
| 排除范围 | 浮点、异常、对象系统、GC、多线程编译、多 ISA |

### 2.4 核心模块与适合复用的部分

核心模块：IR verifier／解释器、离线 stencil 构建、修补记录提取、布局与分支连接、代码内存管理、差分执行、编译成本测量。

可以复用 Clang/LLVM 离线生成模板与 LLVM ORC 作对照。LLVM 不应仅作为项目名称出现：要记录它分别承担离线模板准备、对照后端还是核心优化；模板 JIT 的实现不等于完成 LLVM target 开发。

建议首个扩展只选一个：固定长度表达式链的 stencil 组合、局部布局策略，或按调用次数切换编译模式。首版不同时实现三者。

### 2.5 验证与实验

1. 用独立解释器检验函数结果、分支、循环与数组读取；加入合法随机程序，并设置超时处理无限循环。
2. 对修补后的常量、地址和分支做结构检查，结合真实原生执行。仅反汇编看起来合理不足以证明正确。
3. 比较解释器、模板 JIT、LLVM O0/O2；先统一优化前语义，再比较编译时间和执行时间。
4. 区分进程初始化、LLVM 初始化、模板加载、单函数编译和实际执行；同时报告冷／热状态。
5. 改变程序规模、分支密度、循环次数与重复调用次数，记录最差退化和代码体积。

### 2.6 阶段与退出条件

- M0：在固定平台跑通参考链路，确认模板与重定位记录可获得。
- M1：直线程序差分通过，再支持分支／循环，产出首个端到端版本。
- M2：加入一个局部生成策略，用消融实验解释收益与代价。
- M3：冻结测试集与版本，交付可复现实验和反汇编样本。

如果主要精力长期用于恢复旧工具链、平台格式或重定位兼容性，优先缩小模板种类或更换实现基础。若只会把 IR 交给 ORC，项目仍是基础集成，尚未达到预期深度。

资源：普通 CPU；C++、Clang/LLVM、调试与反汇编工具；不需要 GPU、DSP 板或模型训练。macOS 的可执行内存和代码签名条件、Linux 的 ABI 与目标文件格式要按所选平台实际验证。

资料：[研究概览](https://compilers.stanford.edu/software/copy-and-patch/)、[论文](https://arxiv.org/abs/2011.13127)、[PochiVM](https://github.com/sillycross/PochiVM)、[PEP 744](https://peps.python.org/pep-0744/)、[LLVM ORC](https://llvm.org/docs/ORCv2.html)。

## 3. B：内存预算驱动的计算图编译器

### 3.1 问题来源与独立价值

计算图有多个合法执行顺序。顺序改变张量的存活区间，布局又决定碎片；因此固定顺序下的 allocator 只解决了问题的一部分。

OLLA／后续 MODeL 研究了算子顺序和张量位置的联合优化，相关工作发表于 ICML 2023。这里借鉴其问题建模，以静态 CPU 推理子集实现一个完整系统，不把缩减实验说成复现全部训练结果。

项目问题：**给定纯计算 DAG 和工作内存预算，选择执行次序与内存布局，生成可运行程序；对预算不满足或尚未找到可行解的情况作出准确解释。**

### 3.2 一个简单例子

```text
A = f(x)       # 64 MiB
B = reduce(A)  #  1 MiB
C = g(x)       # 64 MiB
D = reduce(C)  #  1 MiB
y = B + D
```

顺序 `A,C,B,D` 在生成 B 时可能同时保留 A、C、B；顺序 `A,B,C,D` 可以更早释放 A。在输出独立分配、无融合、及时释放且排除输入与 workspace 的理想模型下，峰值分别约为 129 MiB 和 66 MiB。这是概念算例，实际模型应单独核算所有缓冲。

### 3.3 第一版契约

| 项目 | 约定 |
| --- | --- |
| 输入图 | 静态 shape、无环、无副作用；单线程 CPU 执行 |
| 导入范围 | 只保留一个实际验证过的导入器，例如受限 FX 图；内部统一为自有图 IR |
| 算子范围 | add、mul、relu、reduce、matmul 等有限集合；unsupported 明确拒绝 |
| 语义 | 不改变算子内部计算顺序；只重排无依赖操作；禁止随机数、状态修改等隐藏副作用 |
| 预算口径 | 首版限制激活 arena；固定权重、输入输出、kernel workspace 分别报告，不能静默遗漏 |
| 输出 | 执行顺序、生命周期、offset、arena 大小、校验报告、CPU 可执行程序 |
| 结果状态 | 找到可行计划／策略未找到／求解超时／输入不支持；只有可证明时才说不可行 |
| 排除范围 | 训练、动态 shape、异步 kernel、多设备、重计算、offload |

### 3.4 核心模块

图验证与类型/shape 信息 → 依赖与别名建模 → 执行调度 → 生命周期 → arena 布局 → 计划检查 → 执行代码生成。

可以复用现有 CPU kernel。为避免数据被内部重新分配，必须确认 kernel 能写入指定输出位置；不满足时将其临时空间计入模型，或将该算子排除。

独立项目的核心是联合决策与真实执行，不是只画一张内存布局图。建议扩展问题为：**在有限规划时间下，联合启发式能接近什么空间质量？** 小实例精确求解用于校准，不把全图最优作为首版必须条件。

### 3.5 验证与实验

- 合法性：拓扑依赖、生命周期、对齐、固定缓冲、别名和存活对象不重叠。
- 语义：参考执行与新执行逐输出比较；纯整数子集精确比较，浮点沿用预先定义的参考契约。
- 内存：检查实际使用的 offset 与峰值；记录 kernel workspace、输入输出及权重口径。
- 基线：原始顺序＋固定 greedy、只优化顺序、只优化布局、联合方案；保持算子实现一致。
- 规模：从人工 DAG 测边界，再使用多个公开小模型／子图；不能只用有利的分叉图。
- 指标：arena 峰值、规划耗时、运行时间、预算满足比例、超时／失败数量；另报告小图的最优差距或下界。

### 3.6 阶段、资源与限制

- M0：用真实导出图确认算子子集和参考执行，记录张量大小。
- M1：固定顺序＋基础规划＋独立 checker＋真实 arena 执行。
- M2：支持调度变化，并与单独布局优化比较，形成联合决策闭环。
- M3：限定规划时间，完成真实图和小图精确解对照。

资源以普通 CPU、PyTorch 和所选执行/生成基础设施为主。MLIR 可用于后续 lowering，但导入与图规划闭环未成立前，不必自建 dialect。只有计划被真正执行，才算完整集成。

MODeL 仓库已归档，官方说明涉及 Gurobi 版本与许可。若无法使用相同环境，可以复现算法思想并使用不同求解器，但需明确版本、求解状态及与原实验的差异。模拟 arena 减少不等于进程 RSS、GPU 显存或端到端吞吐同比改善。

若默认方案在选定图上已足够好，先研究其适用范围和失败模式，不通过削弱基线制造收益；若缺少真实执行，只剩离线摆放算法，应视为中间里程碑。

资料：[OLLA 论文](https://arxiv.org/abs/2210.12924)、[MODeL](https://github.com/facebookresearch/MODel_opt)、[ExecuTorch 内存规划](https://github.com/pytorch/executorch/blob/main/docs/source/compiler-memory-planning.md)。

## 4. C：列式表达式编译执行引擎

### 4.1 问题来源与独立价值

列式数据上的过滤、算术和聚合可以逐算子执行，也可以融合生成代码。前者通用且启动快，后者减少中间结果，但需要编译与缓存。Apache Arrow Gandiva 是 LLVM 表达式编译器；LingoDB 展示了 MLIR 分层查询编译。

项目问题：**对有限表达式计划生成融合 CPU 函数，并解释批次大小、复杂度和复用次数如何影响解释／编译执行的取舍。**

### 4.2 一个简单例子

```text
price = [100, 200, 300]   # 用整数金额避免此例中的浮点问题
qty   = [  5,  20,  30]

计划：filter(qty > 10) → project(price * qty) → sum
结果：200*20 + 300*30 = 13000
```

逐算子执行可能产生过滤结果和乘法结果；融合执行可以在一个循环中完成。少量数据时，生成函数的开销未必能摊销。输入计划可由结构化 API 构造，不要求先写 SQL parser。

### 4.3 第一版契约

| 项目 | 约定 |
| --- | --- |
| 输入计划 | 类型化的 filter、project、sum/count，单一输入批次 |
| 数据 | 固定宽整数列；首版无 null，随后将 validity bitmap 和三值逻辑作为单独里程碑 |
| 算术 | 明确 wrap／检查溢出策略；参考与所有后端完全一致；首版不含除法、字符串 |
| 输出 | 派生列、selection 或聚合标量，形状与类型可验证 |
| 代码生成 | 融合循环到 LLVM IR/ORC，或受限 MLIR lowering；只选一条主路径 |
| 缓存 | 以规范化计划、类型、语义版本和目标特征构造 key；不能只按表达式文本缓存 |
| 排除范围 | join、group-by、窗口、事务、存储、分布式、完整 SQL |

### 4.4 核心模块、验证与扩展

核心模块包括计划 verifier、独立解释器、常量折叠/CSE、融合边界、循环生成、JIT 生命周期、缓存与实验驱动。已有 Arrow 格式可以复用，但类型／null 语义必须由项目明确约定。

验证时用独立解释器作为主要 oracle，再与支持同一语义的 Arrow 或数据库实现交叉检查。检查空批次、所有行被过滤、溢出边界、非向量长度倍数、缓冲别名与结果长度。引入 null 后，应区分过滤条件未知与 false，以及 sum 对空输入的行为。

基线为逐算子执行、融合解释和融合 JIT；均使用优化构建。现有引擎提供外部参照，但不能只拿完整数据库的端到端时间与小核相比。记录冷启动、编译、预热后执行、临时内存和复用次数，改变批次规模、过滤选择率、表达式复杂度与空值比例。

首版扩展建议选 **编译摊销策略** 或 **null-aware 的融合与向量化** 之一。仅设置一个经验阈值不足以说明策略有效，需要对未参与调参的计划做比较。

### 4.5 阶段、资源与退出条件

- M0：冻结数值与结果语义，解释器支持完整首版子集。
- M1：生成融合函数，覆盖过滤、派生列、聚合并完成差分执行。
- M2：加入规范化缓存；检查等价 key 与不应命中的反例。
- M3：完成一种扩展及相同预算下的实验。

普通 CPU 与 C++/LLVM 即可；Arrow 可选，不需要 GPU 或专用硬件。LLVM、Arrow 开发构建的实际门槛仍需先试。不能因依赖 LLVM 就宣称实现了指令选择或寄存器分配。

若项目主要变成 SQL 解析、CSV 导入或表格界面，说明范围偏移；若只向 Gandiva 提交表达式，核心编译仍由外部系统完成。

资料：[Gandiva](https://arrow.apache.org/docs/cpp/gandiva.html)、[LingoDB 论文](https://www.vldb.org/pvldb/vol15/p2389-jungmair.pdf)、[LingoDB](https://github.com/lingo-db/lingo-db)、[ORC](https://llvm.org/docs/ORCv2.html)。

## 5. D：可独立验证的寄存器分配库与小型原生后端

### 5.1 问题来源与推荐理由

regalloc2 将寄存器分配作为独立组件，明确处理固定寄存器、操作数复用、活跃区间、spill/reload 和验证器。这说明有意义的分配器远不止图着色或区间分配算法：它还要把机器约束、控制流和数据搬运组织成正确的可执行程序。

此方向适合深入传统机器后端。独立项目的价值在于实现完整、可检查的分配链路，并研究一种受控的质量改进；无需声称优于 regalloc2 或 LLVM。代价是接口和正确性负担较大，不能同时扩展多种算法、多个 ISA 和完整 ABI。

### 5.2 简单例子

目标只有两个可分配寄存器，但三个不能重算的值 a、b、c 同时存活，就必须将至少一个值保存到栈，并在后续使用前恢复。仅分配颜色而不生成这些指令，程序并不能执行。

控制流边上的交换也容易出错：某个循环的下一轮需要 `(a,b)=(b,a)`。若 a、b 分别在 r0、r1，直接依次执行 `r0=r1; r1=r0` 会丢失原 r0。分配器需要正确实现并行拷贝，使用临时寄存器或栈槽。

### 5.3 第一版契约

| 项目 | 约定 |
| --- | --- |
| 输入 | 类型化 Machine IR：基本块、整数虚拟寄存器、def/use、分支与块参数 |
| 目标描述 | 一种整数寄存器类、可用寄存器集合；分阶段增加固定寄存器和输入输出复用约束 |
| 语义 | 固定宽整数；循环测试有运行上限；指令与解释器使用同一明确的溢出约定 |
| 输出 | 物理寄存器分配、栈槽、spill/reload、块间搬运及消除块参数后的 IR |
| 执行 | 一个宿主平台的小后端；汇编／机器码编码可复用已有库，清楚标明复用边界 |
| 排除范围 | 浮点／向量类、子寄存器、任意函数调用、完整 ABI、指令调度、多 ISA |

没有调用约定时，测试函数可以采用受限固定签名，内部不调用其他函数。引入调用后，必须增加 caller/callee-saved 和 clobber 模型，不能只给 IR 添加一个 call 节点。

### 5.4 核心模块与验证

核心为 IR verifier、活跃性分析、SSA 线性扫描或另一种单一算法、区间拆分、数据搬运插入、并行拷贝消解和独立 checker。先实现无约束基本块，再扩展 CFG、循环、块参数与约束。

checker 需要检查每个 use 取得的确实是原虚拟值。只检查“同一寄存器中的活跃区间没有交叠”不足以发现搬运遗漏、覆盖或栈槽复用错误。可以借鉴 regalloc2 的数据流检查思路，但不要把自己实现的有限检查称为全程序形式化证明。

两条验证路径应同时存在：分配前后的 IR 解释执行比较，以及原生代码与独立解释器比较。随机生成器先保证输入 IR 合法；加入高寄存器压力、循环内 spill、固定寄存器冲突、复用操作数、关键边与拷贝环等定向测试。

### 5.5 基线、指标与可控扩展

基线按三层设置：全部放栈的正确实现、简单线性扫描、改进实现。与 regalloc2 比较时，只使用双方能表达的相同约束，单列适配成本与不支持的指令。

记录分配耗时、峰值内存、spill/reload 数、搬运数、栈帧大小和原生程序运行时间。静态指令数只是代理指标，不能直接等同于加速。可选扩展为循环权重驱动的 spill 选择，或更好的区间拆分；首版只选一个。

### 5.6 阶段、资源与退出条件

- M0：Machine IR verifier、解释器和全部放栈的执行路径。
- M1：基本分配器、CFG 与块参数搬运，差分验证通过。
- M2：加入约束及独立 checker，针对失败输入自动缩减。
- M3：一个宿主后端、一种改进与质量／时间权衡实验。

普通 CPU 即可，主要依赖 C++、汇编工具与反汇编器；不需要专用硬件。平台 ABI 和可执行内存仍需先试。若只能完成“为几张图着色”的演示，规模偏小；若迟迟卡在编码器和 ABI，应复用这些外围模块，保留分配与验证的核心。

资料：[regalloc2](https://github.com/bytecodealliance/regalloc2)、[设计说明](https://cfallin.org/blog/2022/06/09/cranelift-regalloc2/)、[SSA 线性扫描论文](https://c9x.me/compile/bib/Wimmer10a.pdf)。

## 6. E：受限 RTL 的编译式仿真器

### 6.1 问题来源与推荐理由

Verilator 的内部设计说明详细讨论了调度、时序区域、依赖分析和 C++ 生成。它说明 RTL 仿真本身就是编译与运行时相结合的问题：将硬件的并发更新转换为宿主机器上的顺序计算，同时保持可观测行为。

此方向与已有 C++、EDA 经验衔接最自然，CPU 即可完成完整实验。合理定位是**明确受限语义下的仿真编译器及一种调度优化**。完整 SystemVerilog 仿真器范围过大；成熟工具已经有大量优化，不能把一个简单电路上的优势推断成普遍优势。

### 6.2 简单例子

两个寄存器在同一上升沿执行：

```verilog
a <= b;
b <= a;
```

原状态为 a=1、b=2 时，新状态应为 a=2、b=1。将其直接翻译成顺序赋值 `a=b; b=a;` 会得到 a=2、b=2。正确的编译需要区分旧状态、下一状态和统一提交。

进一步说，提交后组合输出可能改变。测试接口应约定读取的是“时钟沿后组合逻辑稳定”的输出，不能把边沿前输出和边沿后输出混在一起比较。

### 6.3 第一版契约

| 项目 | 约定 |
| --- | --- |
| 输入 | 已展平的类型化网表／硬件 IR；只接入一个已有前端，例如经过固定 Yosys 流程的 JSON |
| 值模型 | 二值、1—64 位 bitvector；位宽、截断、扩展与移位语义逐项定义 |
| 时序 | 单时钟上升沿、同步复位；寄存器初值由规定的复位序列建立 |
| 组合逻辑 | 无环；明确支持算子集合，非法输入或不支持的单元直接拒绝 |
| 输出 | C++ 模型、初始化／复位接口、逻辑周期 step 与观测接口 |
| 排除范围 | X/Z、未初始化可观测状态、延迟语句、异步复位、多时钟、组合环、存储器、UVM |

step 的约定必须包括：输入在何时设置、旧状态如何读取、何时统一提交、何时稳定输出。对于 64 位移位、窄位取反等，生成的 C++ 不能依赖未定义行为。

使用 Yosys 作为前端并不会自动保证源 RTL 的全部语义保留。固定前端版本和变换序列，检查 X／未初始化处理方式；首版只接收能落到上述契约的设计。

### 6.4 核心模块与验证

核心模块为网表导入与 verifier、位宽处理、组合依赖图、拓扑调度、状态拆分与提交、C++ 生成和模型驱动。先实现每周期完整求值，再选择一种减少无效计算的方案。

独立解释器直接执行规范化 IR，负责检验代码生成；对语义交集内的原始 RTL，再使用 Verilator 检验端到端行为。两者解决不同问题：仅与自己的解释器比较，可能共同继承导入错误；仅与外部工具比较，又可能难以定位语义差异。

定向测试覆盖状态交换、反馈计数器、截断／符号扩展、拼接、位选择、复位、边界移位、多个输出共享逻辑。随机输入从合法复位状态开始，比较多周期的可观测轨迹。遇到不一致时保存输入序列并缩减电路。

### 6.5 基线、指标与可控扩展

内部基线为同一 IR 的全拓扑求值。可先研究输出／下一状态所需的逻辑锥裁剪，再考虑活动驱动的 dirty-set 调度；第一阶段只选择一种。后者可能在低活动率电路上节省计算，也可能因分支与标记开销而退化，应把退化条件列入结论。

外部基线为相同二值子集、相同激励与观测条件的 Verilator 模型。记录生成／编译时间、生成代码大小、每秒周期数、每周期实际求值节点数与宿主内存。使用相同优化级别，统一波形开关和驱动开销，不能拿自己的无波形模型对比对方开启波形的模型。

电路集合应覆盖数据通路、控制逻辑、不同位宽与活动率。单个计数器只够打通链路；从公开设计中抽取子电路时，要记录来源、许可、删减步骤与保留下来的行为。

### 6.6 阶段、资源与退出条件

- M0：冻结语义，导入一个小电路，参考解释器与外部结果一致。
- M1：生成可编译模型，完成多寄存器、多周期与位宽测试。
- M2：实现一种调度／裁剪优化，验证开启前后的完整轨迹。
- M3：加入多类电路、参数扫描和负面结果，形成可复现实验。

需要 CPU、C++ 编译器、Yosys 和 Verilator；首版不需要 FPGA、开发板、商业许可证。Linux／WSL 是优先试验环境，Mac 是否直接可用以实际构建为准。若大部分时间消耗于完整 HDL 前端，应改为稳定的规范化 IR 输入；若只生成若干 Verilator 命令，自己的编译核心仍然不足。

资料：[Verilator 内部设计](https://github.com/verilator/verilator/blob/master/docs/internals.rst)、[模型连接接口](https://verilator.org/guide/latest/connecting.html)、[Yosys](https://github.com/YosysHQ/yosys)、[CIRCT](https://circt.llvm.org/docs/)。

## 7. F：组合逻辑优化与 LUT 技术映射

### 7.1 问题来源与推荐理由

ABC 和 Yosys 的综合链路将逻辑优化、技术映射和等价验证放在同一个可执行流程中。其核心问题十分明确：给定一个布尔网络，保持函数不变，将其实现为更合适的目标单元网络。

对于小项目，固定为 K 输入 LUT 比直接做标准单元映射更可控：可以暂时避开 Liberty 时序模型、负载估计与物理实现，又能保留 cut 枚举、动态规划、共享逻辑和面积／深度权衡。若偏好图算法和综合，这个方向可以替代 E 成为首选。

### 7.2 简单例子

`f=(a & b) | (a & c)` 可以改写为 `a & (b | c)`。在简单二输入门计数中，后者可能减少一个节点；但对于 4 输入 LUT，两种表示都可能只需要一个 LUT。

这个例子揭示了目标函数的重要性：AIG 节点数减少，不等于映射后的 LUT 数减少；LUT 层数减少，也不自动等于实际器件频率提升。项目应直接测量所声称优化的层次。

### 7.3 第一版契约

| 项目 | 约定 |
| --- | --- |
| 输入 | 二值、无环组合网络，首版选择一种 AIGER ASCII 等标准格式；前端转换可复用 Yosys／ABC |
| 目标 | 固定 K=4 的 LUT 网络，后续再把 K 参数化 |
| 输出 | 可被独立读取的 LUT 网表、每个 LUT 的真值表、连接关系、面积与层数报告 |
| 正确性 | 输出网络与输入网络在所有输入组合上的输出函数一致 |
| 排除范围 | 寄存器重定时、顺序综合、don't-care 优化、标准单元库映射、布局布线 |

导入后验证拓扑、输入输出标号、反相边和常量。输出格式可以选 BLIF，但必须让独立工具实际读回并比较，不能只输出一张摘要表。

### 7.4 核心模块与验证

核心为 AIG 导入／结构哈希、受限逻辑重写、K-feasible cut 枚举、有界优先 cut 集、映射选择与面积恢复。第一版可先不做重写，先让映射器形成完整闭环。

树上的动态规划结果不能直接当成共享 DAG 的全局最优解；面积恢复需要明确如何估计共享与引用次数。若采用启发式，应清楚报告其适用范围与运行代价。

小网络穷举所有输入；大网络先随机仿真，再构造 SAT miter。miter 对应输出异或，SAT 返回反例，UNSAT 才支持该组合网络的等价结论；超时或 unknown 不能按验证通过处理。映射器自己的真值表计算和输出解析也需要独立检查。

### 7.5 基线、指标与可控扩展

内部基线为简单贪心映射和深度优先映射；外部基线使用 ABC 的固定映射流程与相同 K。冻结输入预处理，分开报告“映射器本身”和“重写＋映射”两组实验，避免把前处理优势归因于映射策略。

指标包括 LUT 数、逻辑层数、映射耗时、内存、cut 数和验证结果。LUT 层数属于结构延迟指标，未经器件映射与时序分析不能写成纳秒或最高频率。可控扩展选择深度约束下的面积恢复，或有界 cut 筛选策略；不同时开展全套重写算法。

公开基准选取时记录原始出处和许可，覆盖算术、译码、控制与共享逻辑；不要只使用自动生成的平衡树。调参与最终比较保留不同电路，并公开失败和超时样本。

### 7.6 阶段、资源与退出条件

- M0：导入、解释求值、格式往返和独立等价检查。
- M1：cut 枚举与基础映射，输出可读回的 LUT 网表。
- M2：一种受控策略改进及正确性检查。
- M3：与 ABC 的同条件比较，给出面积／深度／时间权衡。

普通 CPU、C++ 与 SAT 求解器即可；Yosys／ABC 提供转换和参照。首版不需要 FPGA、开发板、Liberty 文件或商业工具。只有将结论扩展到具体器件 PPA 时，才需要补充对应工具与约束。

若最终只有 ABC 脚本组合，难以体现自己的映射实现；若目标变成“所有电路都优于 ABC”，则对首版要求过高。完整实现并解释改善与退化区域，已经构成有意义的技术成果。

资料：[ABC 官方介绍](https://people.eecs.berkeley.edu/~alanmi/abc/abc.htm)、[ABC 源码](https://github.com/berkeley-abc/abc)、[Yosys 的 ABC 综合流程](https://yosyshq.readthedocs.io/projects/yosys/en/latest/using_yosys/synthesis/abc.html)。

## 8. G：资源约束的静态 HLS 后端

### 8.1 问题来源与推荐理由

CIRCT 的 Scheduling 基础设施显式描述操作依赖、调度问题和资源约束；XLS 展示了从类型化计算到硬件实现、调度和代码生成的完整技术路径。它们支持这个问题的实际意义，但并不意味着两套系统与这里的 FSM 资源共享模型完全相同。

小项目可聚焦：将静态算术 DAG 调度到有限数量的算子，生成可仿真的控制器与数据通路。它比仅求一张调度表完整，又比支持 C/C++、循环、访存和流水的通用 HLS 更可控。需要同时处理调度与 RTL 正确性，因此建议放在 E／F 之后考虑。

### 8.2 简单例子

计算 `y=a*b+c*d`，输入为 8 位无符号数，乘积为 16 位，求和为 17 位。假定乘法模块延迟 2 周期、启动间隔 2 周期，加法模块延迟 1 周期：

| 配置 | 乘法启动时刻 | 加法启动时刻 | 结果可用时刻 |
| --- | --- | --- | --- |
| 两个乘法模块 | 两个乘法都在 t=0 | t=2 | t=3 |
| 一个共享乘法模块 | 分别在 t=0、t=2 | t=4 | t=5 |

共享方案需要保存第一项乘积，并在不同周期切换乘法模块的输入。这是调度、绑定、寄存器保存和控制生成共同作用的结果。表中数值是明确定义的周期模型示例，不是某个器件的测量结果。

### 8.3 第一版契约

| 项目 | 约定 |
| --- | --- |
| 输入 | 类型化、无环、无副作用的整数算术 DAG；明确位宽、截断和扩展 |
| 约束 | 算子种类、数量、延迟和启动间隔；每种模块有可执行功能／时序模型 |
| 输出 | 调度、资源绑定、寄存器保存方案、FSM＋数据通路 RTL，以及测试接口 |
| 协议 | start/done，一次只处理一个事务；结果有效时刻与输入采样时刻明确 |
| 排除范围 | 任意 C/C++ 输入、循环流水、访存与别名、多事务重叠、异常、动态控制 |

算子延迟不能仅在调度器中写一个数字，而 RTL 中仍当作任意组合表达式使用。首版可用公开实现的寄存器化算子模块，并验证其延迟与可接受输入间隔；模块的周期模型和综合后的实际时序是两个层次。

### 8.4 核心模块与验证

核心为 IR verifier、依赖和资源模型、资源约束 list scheduler、算子绑定、值生命周期与保存、控制器／多路选择器生成、RTL 输出。可以先为所有中间结果保留独立寄存器，暂缓寄存器共享。

独立调度检查器验证：消费者启动不早于生产者结果可用；资源数量和启动间隔合法；每个被使用的值仍有有效存储。功能解释器计算数学结果，RTL 仿真器按 start/done 收集结果；两种实现可能延迟不同，应按事务对应输出，不能逐周期直接比较。

检查复位、忙时输入变化、反复启动、不同算子延迟、结果宽度和资源不足。可加入有界时序性质检查，但有界通过只能说明相应展开深度内未发现反例。

### 8.5 基线、指标与可控扩展

内部基线为简单优先级 list scheduling；改进方案必须在同样资源预算下比较。无限资源 ASAP 可作为延迟下界参照，不能拿它与单算子方案直接宣布优劣。小 DAG 可用穷举或约束求解获得对照，但求解超时需要保留。

指标为事务延迟周期、算子数量、寄存器数、多路选择器规模、调度时间与生成规模。可以再用 Yosys 映射得到相同库下的面积代理；没有物理工具与完整约束时，不宣称实际 PPA 改善。

可选扩展为关键路径／生命周期感知的调度优先级，或者固定延迟预算下的资源选择。首版只研究一种，展示不同资源预算下的 Pareto 权衡，并验证每个输出 RTL 的功能。

### 8.6 阶段、资源与退出条件

- M0：解释器、算子时序模型与不共享资源的 RTL。
- M1：资源约束调度、共享绑定与 FSM，端到端仿真一致。
- M2：独立约束检查和不同延迟／预算组合。
- M3：一种策略扩展、消融与可综合性检查。

CPU、C++、Verilator 和 Yosys 足以覆盖首版，不要求开发板或商业 HLS。CIRCT／XLS 可作为架构参照；无需为了使用它们而先构建全套工具链。若选择直接扩展其 IR，应先验证依赖构建成本。

若只输出甘特图而不生成可运行硬件模型，链路不完整；若引入循环流水、内存调度和多事务重叠后无法闭环，应退回静态单事务模型，而非靠手工修改生成 RTL 完成演示。

资料：[CIRCT Scheduling](https://circt.llvm.org/docs/Scheduling/)、[XLS](https://google.github.io/xls/)、[XLS 调度说明](https://github.com/google/xls/blob/main/docs_src/scheduling.md)。

## 9. 统一验证与实验协议

### 9.1 将四种证据分开

| 层次 | 要回答的问题 | 需要保留的材料 |
| --- | --- | --- |
| 输入与语义 | 输入是否属于支持范围，语义是否唯一？ | 格式说明、verifier、正反例、拒绝原因 |
| 编译决策 | 调度、布局、分配和映射是否满足约束？ | 独立 plan checker、约束模型、失败定位 |
| 执行结果 | 生成产物是否保持约定行为？ | 独立解释器、差分轨迹、外部参照、反例 |
| 成本与效果 | 在什么条件下改善，又在什么条件下退化？ | 固定基线、消融、原始数据、环境与脚本 |

不能用一个层次替代另一个层次。规划合法不代表生成代码正确；仿真结果一致不代表满足资源预算；随机测试通过不代表等价证明；静态节点数更少不代表实际更快。

已有正常链路时，先固定它的输入、变换、执行与观测方式，再更换其中一个模块。对照应以行为链路为基线，不能仅比较生成代码的形式。

若设计兜底路径，应明确记录何时触发、采用了什么路径、结果属于哪组数据。兜底不能绕过待检验的主路径，不能把回退后的成功执行计入该优化的通过率或性能结果。

### 9.2 正确性判据

- 整数与 bitvector 尽量逐位一致，事先固定宽度、符号、截断与溢出语义。
- 浮点如确需引入，应先规定误差、NaN/Inf、归约顺序与 fast-math 选项；不能测完后放宽阈值。
- 对计划的验证尽量独立于生成算法：调度器产生计划，checker 从约束重新判断合法性。
- 区分通过、反例、非法输入、不支持、超时、未知；只有充分依据才报告“不可行”。
- 所有发现过的错误保留最小回归样本；随机测试记录种子，反例尽量自动缩减。

参考实现不宜与优化实现共享同一套复杂变换逻辑，否则容易共同出错。格式、基础类型等可以复用，关键语义与决策检查应具有独立性。

### 9.3 基线和数据集合

至少保留一个简单但完整的内部基线，以及一个语义条件可对齐的外部参照。外部参照用于理解位置，不要求所有项目都在第一版完全适配成熟系统。

电路／程序集合按用途分开：小规模穷举集用于发现错误，定向集覆盖已知边界，代表性集合用于成本比较，保留集用于检验调参后的结论。随机生成器不能替代所有真实输入，也不能只留下有利案例。

固定输入前处理与工具版本。修改前端、输入、优化级别和目标约束会同时改变多个因素，应作为单独实验。每一种新策略至少比较“全部关闭”和“只开启这一项”；增加多项策略后，再逐项消融。

### 9.4 测量口径与复现材料

每次运行记录：提交版本、依赖版本、宿主 CPU／架构、OS、内存、编译选项、线程数、随机种子、输入校验和与资源约束。编译器构建耗时、项目处理输入的编译耗时、产物执行耗时应分别报告。

冷启动和预热分开。重复测量保存分布，通常给中位数与分位数；样本很少时不要用精确分位数制造确定性。短小核的驱动与计时开销需要量化。WSL／虚拟机中的结果保留环境说明，不能解释成跨平台的稳定时序保证。

内存指标写清测量范围：B 的 arena、D 的栈槽与进程 RSS 含义不同。对于 E／G，宿主仿真时间、硬件周期数、综合面积代理和实际时序也分别报告。

每张结论图应能回溯到输入、配置、原始结果与生成脚本。没有实际执行的分析标为假设或待验证；没有改善时，如实说明质量／时间取舍和失败区域，完整可靠的系统实现依然有价值。

## 10. 资源、依赖与 MLIR 的使用边界

### 10.1 首次环境试验

先确认 Mac 和 WSL 的架构、可用内存、磁盘、编译器与工具版本，再选择主环境。WSL 的文件系统位置和跨系统 I/O 会影响构建与运行，先用小例验证。构建依赖不等于项目核心进展，应设置单独的环境试验出口。

| 方向 | 第一版主要依赖 | 最先确认的资源问题 | 可以暂时避免的依赖 |
| --- | --- | --- | --- |
| A | Clang/LLVM、反汇编器、宿主可执行内存接口 | stencil 构建兼容性、宿主 ABI、内存执行权限 | 多 ISA、完整语言运行时 |
| B | CPU kernel、一个真实图导入器；求解器可选 | 输出缓冲／workspace 能否受控、真实图能否落入子集 | GPU、训练栈、商业求解器 |
| C | LLVM ORC；Arrow 可选 | LLVM 构建、批数据接口与编译成本 | 完整数据库与 SQL 前端 |
| D | C++、汇编／编码工具、执行与反汇编接口 | 宿主目标的小指令集合和调用边界 | 多类寄存器、多平台后端 |
| E | C++、Yosys、Verilator | 网表导入与二值复位契约 | FPGA、商业仿真器、完整 HDL 前端 |
| F | C++、ABC／Yosys、SAT 求解器 | 输入格式往返、等价检查能否独立运行 | FPGA、标准单元库、物理工具 |
| G | C++、Verilator、Yosys | 算子时序模型与生成 RTL 能否对齐 | 商业 HLS、开发板、复杂存储系统 |

不提供未经构建验证的精确内存下限。优先使用可复现的稳定版本或预构建包；确需源码构建时，只启用实际使用的目标和组件。记录依赖及输入材料的许可，公开派生样本时保留来源与修改说明。

### 10.2 不把 MLIR 作为强制前置条件

| 方向 | MLIR／相关基础设施可能提供的价值 | 第一版可以自行实现的部分 |
| --- | --- | --- |
| A | 接收已有计算 IR、作为优化对照 | 小型 IR、stencil 布局与修补 |
| B | shape/type 表达、bufferization 与后续 lowering | 静态图、预算调度与 arena 规划 |
| C | 表达式／循环／向量的分层 lowering | 类型计划、融合循环和 LLVM IR 生成 |
| D | 接收上游结果；机器级接口另行定义 | Machine IR、分配库与 checker |
| E／F | CIRCT 的硬件类型、组合逻辑与模块表示 | 受限网表、调度或 cut 映射 |
| G | CIRCT 的问题建模与硬件表示 | 静态 DAG、资源模型、FSM 生成 |

只有当基础设施解决明确问题时才引入。引入后需要解释新增的表示层、合法化边界和 lowering 责任；只定义 dialect 后调用已有后端，可能把主要实现留给了外部系统。另一方面，重复开发成熟 parser、编码器或容器也不必然增加技术深度。

## 11. 如何缩小到一个可启动的题目

### 11.1 当前建议

**先在 E、A、B 中选一个，不同时启动三个。** E 最贴近已有 EDA／C++ 基础；A 最接近原生执行与机器码；B 最容易连接计算图、资源预算和执行规划。F 可以在更偏好综合算法时替换 E。

| 判断条件 | 更倾向的选择 | 需要接受的代价 |
| --- | --- | --- |
| 希望复用电路语义经验，并尽早形成 CPU 上的验证闭环 | E | 必须严守受限 RTL 语义，和成熟仿真器公平比较 |
| 希望直接处理原生代码、重定位和执行成本 | A | 宿主平台与模板工具链可能先占较多时间 |
| 对资源约束、图算法和内存生命周期更感兴趣 | B | 必须让计划落实到真实缓冲与执行，不能停在模拟器 |
| 更偏好布尔网络、综合与等价验证 | F | 结构指标与实际器件性能需严格区分 |
| 明确希望深入机器寄存器与数据流修复 | D | 第一版正确性负担大，原生执行闭环不可省略 |
| 更愿意研究批处理、融合与编译摊销 | C | 容易扩成数据库，要主动限制前端和算子 |
| 更偏好资源共享、控制器和硬件生成 | G | 同时承担调度与 RTL 验证，范围控制最关键 |

这是实现可行性的初排。算法是否能产生新结果、外部基线是否容易对齐、实际工具链是否兼容，仍需要小试后判断。公开系统证明问题重要，不证明这里提出的具体改进还未被解决。

### 11.2 五个阶段门槛

| 阶段 | 必须得到的结果 | 不满足时如何收缩 |
| --- | --- | --- |
| P0：环境与参照 | 在目标机器运行最小参考路径；确认输入、输出和依赖版本 | 更换稳定版本或主环境，删去非必要依赖；不无限修复旧工具链 |
| P1：语义闭环 | 一个小输入经过完整链路，与独立参照一致；非法输入有明确拒绝 | 缩小算子／语言子集，不以手工修产物完成演示 |
| P2：自身核心 | 核心分析／变换／生成由项目承担，并覆盖多类输入 | 识别仍由外部工具完成的关键模块，补齐一个主要环节 |
| P3：单项扩展 | 一种改进、一个强度合理的基线与独立正确性检查 | 先保留完整复现，不强求新算法或额外功能 |
| P4：可复现发布 | 构建、验证、实验可按文档执行；结论能追到原始数据 | 删去无法复现的结论，公开当前限制与失败样本 |

不在环境参数和可投入时间未知时承诺固定周数。每阶段用可检查产物判断进度。P1 之后再决定是否增加 MLIR、多平台或更复杂数值类型；P3 之前不同时引入多个优化方向。

### 11.3 第一轮小试的具体产物

若选择 E，先做“规范化小网表 → 独立解释执行 → C++ 模型 → 多周期轨迹比较”。输入至少包含双寄存器交换与一段组合逻辑，固定复位和观测协议。此时只验证导入与语义，不以性能作为通过条件。

若选择 A，先做“一种宿主平台上的几个 stencil → 一条包含条件分支的原生函数 → 与解释器一致”。把模板提取、修补和真实调用全部走通，不能用预先写好的完整函数替代拼接路径。

若选择 B，先做“一个受支持的真实图子集 → 固定顺序的内存计划 → 明确输出缓冲的 CPU 执行”。把 arena 上界、kernel workspace 与实际分配对齐，再研究新的调度顺序。

这三种小试都不要求先创建完整生态。能否稳定复现与清楚定位错误，比演示界面或仓库规模更有判断价值。

## 12. 成果形态与辅助扩展

### 12.1 三种实现方式并不冲突

| 方式 | 适合条件 | 自己需要承担的核心 | 主要风险 |
| --- | --- | --- | --- |
| 独立专项工具／库 | 输入输出契约可以独立定义 | 核心算法、执行闭环、验证接口与实验 | 外部语义适配不足，成为孤立样例 |
| 成熟项目的专项分支 | 已有系统具备输入、执行和基线，且扩展点清楚 | 一个完整模块／策略及稳定集成 | 版本维护成本，改动被大系统掩盖 |
| 方法复现后做扩展 | 论文算法、代码和数据足够明确 | 复现边界、差异解释、一项受控扩展 | 旧依赖、缺失数据、把迁移差异当算法优势 |

可以先独立实现核心库，再接入成熟项目；也可以先复现，再拆出可复用组件。来源必须清楚：哪些代码来自上游、哪些只是重新实现、哪些属于新增策略。是否被外部合入与系统本身是否完整是不同维度，不把它作为首版能否结束的唯一条件。

### 12.2 信号处理与 Agent 的合适位置

信号处理经验可以提供算子语义和测试直觉，例如把有限长度 FIR 的整数核作为 A／G 的一个样例，但它不能替代多类输入。第一版没有必要引入 DSP 板、嵌入式工具链或音频实时性要求；否则资源门槛和验证目标都会改变。

Agent 更适合在系统已有正确性检查后，帮助生成合法输入、寻找策略参数或缩减反例。若它负责选择 pass／调度策略，仍需固定调用预算、保留独立 checker，并与无模型搜索比较。仅串接模型调用与工具流程，不会自然增加编译中后段深度。

当前不将二者设为主方向：它们可以增强选定问题，但也容易把精力移到音频产品、设备接入或模型服务。所有扩展都应回答：它改变了哪个编译决策、怎样保持语义、用什么指标检验。

## 13. 最终验收与立项记录

### 13.1 建议目录与材料

以下为未来独立项目的目录建议，不表示当前已创建或实现：

```text
README.md             # 支持范围、最小运行路径、限制
src/                  # 核心表示、分析、变换与生成
tests/                # verifier、差分、回归与边界输入
benchmarks/           # 输入清单、来源、许可与固定配置
scripts/              # 环境检查、批量验证和结果生成
docs/design.md        # 契约、模块责任与关键取舍
docs/evaluation.md    # 基线、环境、口径和结论
results/              # 可追溯的原始数据与摘要；按规模选择归档方式
```

### 13.2 立项前填写

| 项目 | 需要写下的内容 |
| --- | --- |
| 问题 | 一句话描述具体约束下的输入、目标和输出 |
| 依据 | 原始系统／论文链接；问题存在与改进空白分别有什么证据 |
| 首版语义 | 类型、控制流、数值、状态、错误与资源模型 |
| 核心责任 | 自己实现什么，哪些模块复用外部系统 |
| 基线 | 可在同一环境实际运行的内部／外部参照 |
| 正确性 | 独立 oracle、约束检查器、差分与证明各负责哪一层 |
| 效果 | 首要指标、次要指标、不可从结果推出的结论 |
| 环境 | 平台、依赖、构建和执行资源；尚未确认的条件 |
| 首个里程碑 | 一个可独立检查的小型端到端产物 |
| 收缩边界 | 删除什么仍保留问题核心；哪些情况应换题 |

### 13.3 首版完成标准

1. 明确接受一类输入，不支持的输入有可复现的拒绝行为。
2. 产生真实可执行／可消费产物，自身核心参与主路径。
3. 有独立正确性参照、边界测试与失败回归，而非只通过一个演示。
4. 有固定条件的基线、至少一项消融、原始数据与复现说明。
5. 能解释适用范围、退化案例与未覆盖能力；测量和假设清楚分开。
