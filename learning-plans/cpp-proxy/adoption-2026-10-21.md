# Proxy 的业界采用与普及障碍

[学习入口](README.md) · [资料索引](resources.md)

核查日：2026-10-21，Asia/Shanghai。范围：微软/维护者公告、GitHub 公开项目的 issue/PR 及部分源码、包管理器反向依赖、版本迁移和构建反馈。没有私有部署数据，也没有可支持市场占有率估算的全面样本。

## 结论

**有生产使用声明，也有微软之外的真实项目接入；公开生态证据仍不足以称为广泛采用的通用基础设施。**更适合将其定位为已有落地的专门多态工具。这里的判断针对公开可见性，不能外推成“所有私有工程用得少”。

### FISCO 源码核对

目标分支通过 GitHub REST PR 接口确认。另查默认分支 master，提交 `58920ae185a3fdeba544d828907ab3e208a586a8`：上述两个文件路径不存在，检查的根 vcpkg.json / Entry.h 没有 Proxy 标记。这个抽查不是整个 master 的无依赖证明，但足以要求保留“release 分支接入”的限定。

PR 文档中的“零开销”“proxy 需要 C++23”等措辞不原样采信：Proxy 官方定位为 C++20，具体编译器可能使用扩展；性能仍需等价工作负载的测量。

## 如果尚未广泛采用，可能为什么？

没有找到覆盖未采用团队的调查，所以下表是**工程机制分析，结合真实反馈，不是已证实的全行业因果排序**。

### 1. 它解决的需求有边界，现有方案经常已经够用

Proxy 优势集中于：需要运行时开放类型集合，同时不想要求具体类型继承接口，或者希望统一多种表达式及句柄策略。若类型在编译期已知，模板即可；类型集合封闭时可用 variant；稳定继承层次可以继续 virtual；单个可调用操作已有 function 系列。

因此采用要回答“当前痛点值不值得引入一套通用设施”。FISCO #5257 提供的具体动机是减少重复的手写类型擦除转发代码。这是清晰的收益来源，但不是所有工程都有同样的重复层。

### 2. 接入成本包括团队理解和开发工具体验

facade、dispatch、限定符、存储和复制约束都需要维护者理解。非侵入式接口也失去了一部分传统继承带来的工具提示：用户在 [issue #225](https://github.com/microsoft/proxy/issues/225)明确询问如何检查实现满足接口，并提到 IDE 自动补全实现方法的困难。该反馈不是当前所有 IDE 都不可用的证明，但揭示了真实工作流成本。

FISCO #5339 因其 facade 中同名重载访问器的歧义，将两个 remove 操作改为不同名称后继续简化包装。只据此说“该项目的这次接入需要改接口”，不归纳成库不能处理函数重载。

### 3. 模板的编译与体积成本需要计入收益

ClickHouse 提议者担忧二进制大小，但未测量。更扎实的构建证据是 [ngcpp PR #32](https://github.com/ngcpp/proxy/pull/32)：对模板实例化设施做优化，尤其改善多 convention 的编译基准；已合并并包含于后续发布。因此“曾有这项成本并持续优化”有据可查，“目前仍有同等严重问题”不能据此断言。

### 4. 工具链和版本迁移会抬高引入门槛

官方要求 C++20 与相应编译器版本，仍使用旧标准/工具链的项目无法直接采用。Proxy 3 → 4 存在 API 变化，[issue #300](https://github.com/microsoft/proxy/issues/300)记录了多库依赖不同主版本的冲突担忧。项目后来通过版本化命名空间及宏等设施支持共存，应同时看到问题和解决方案，不能把历史问题列成永久缺陷。

本专题 2026-10-20 实测 Apple Clang 的 C++20 扩展警告；FISCO #5247 也记录过扩展警告的编译配置调整。这是需要试编译和纳入构建政策的接入细节，不是“库只能用 C++23”。

### 5. 性能优势未必构成迁移动机

[官方性能文章](https://devblogs.microsoft.com/cppblog/analyzing-the-performance-of-the-proxy-library/)是特定编译器、对象大小和负载下的微基准。内联存储、分配策略和元数据位置都可能影响结果；业务方法较重时，分派差异可能不重要。已有正确、稳定的 virtual 路径若不是瓶颈，切换需要额外的维护理由。

### 6. 所有权和长期依赖责任仍由项目承担

Proxy 可以表达拥有和借用，但不消除悬垂、共享可变状态或同步问题。相同 proxy 类型可以装不同所有权策略，API 契约仍需明确。微软归档、转由 ngcpp 维护是事实；它可能让一些团队重新评估依赖治理，这是推断，不能宣称微软已停止内部使用或项目没人维护。

## 对学习投入的建议

先掌握其思想与一个典型接口即可判断价值：理解“编译期检查 + 类型擦除 + 句柄生命周期”，自己写一个 facade，比较现有 virtual 或手写 wrapper 的复杂度。只有遇到真实接入需求，再深入全部 skills 与底层优化；无需因为它曾由微软开发就优先全量迁移。

## 检索方法与限制

- 普通网页搜索使用库路径及精确 API 名称，网络代理同名噪声很大。
- 补充 GitHub REST issue/PR 搜索，查询 `PRO_DEF_MEM_DISPATCH`、`msft_proxy4`、`ngcpp/proxy` 以及 `microsoft/proxy + polymorphism`，排除库自身两个仓库。逐项区分包管理、实验、提议和实际接入。
- 对关键 PR 读取 `merged_at`、`base.ref`、`merge_commit_sha`，避免将 closed 误作 merged，或将 release 分支误作默认主干。
- GitHub dependents 网页本次无法获取；没有完整的跨 GitHub 代码搜索结果。issue 搜索会漏掉没有讨论过依赖的项目，不能据其命中数计算采用率。
- vcpkg 的 Used By 当时仍显示无其他包。这只覆盖包目录能识别的反向依赖；FISCO 的 manifest 依赖就是为什么不能把这个数字当成全世界使用者数量。
- 未核查 FISCO 对应版本的正式发行/链上部署，未测量其体积或性能；未发现真实“因问题放弃 Proxy”的充分案例集合，故不虚构未采用团队的理由。
