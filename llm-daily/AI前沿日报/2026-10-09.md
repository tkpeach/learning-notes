# 业界进展

### NVIDIA 公布 Nemotron 面向 IOI 与 IMO 的专门化训练和推理链

**质量：A｜重要性：高｜此前漏报，原始发布：2026-10-07。** [NVIDIA 团队技术说明](https://huggingface.co/blog/nvidia/nemotron-ioi-and-imo-2026)把两项竞赛成绩与具体方法和公开产物放在一起：IOI 2026 的 Nemotron‑3‑Ultra‑CC 在现场、前瞻性测试中得 535.4/600，高于 361.12 的金牌线；这是非官方、未列入正式排名的测试。IMO 2026 系统得 30/42，越过 29 分金牌线；其自然语言证明由官方竞赛阅卷员评分。这两类结果分别测试可执行程序和数学证明，难度高于普通静态问答，但不应合称为“一个模型同时拿下两项官方金牌”。

**增量来自模型与推理过程共同设计。** IOI 路径从 22,000 道竞赛编程题及合成推理轨迹训练专门模型；文中给出 Nano 模型在 2025 年题目上由未后训练的 130 分，经 SFT 升到 280 分、RL 到 291 分，再经 GenCorrect 的生成—执行/反馈—修正达到 468 分。更大规模的 Ultra‑CC 主要由 SFT 专门化，再用相同类型的反馈循环取得 2026 年成绩。IMO 路径用 15,818 道独特证明题形成约 41.5 万条筛选后 SFT 样本，并在能力边界附近的 9,597 道题上进行 RL；最终把通用、SFT 与 RL checkpoint 组合成生成、批评、修订和高计算量最终筛选系统。作者明确说明未使用形式化证明器、外部工具或互联网。

**证据与迁移边界。** [IMO checkpoint、数据和 200 题基准合集](https://huggingface.co/collections/nvidia/nemotron-labs-imo-2026)与[NeMo‑Skills 推理流程](https://github.com/NVIDIA-NeMo/Skills/tree/main/recipes/nemotron-imo-tts)为研究者提供了审查入口；IOI 竞争编程模型与论文也在原文中链接。公开资产让训练专门化和测试时搜索的贡献有机会被拆开验证，但发布页未给出足以比较各环节单位成本的统一预算，也未证明在开放式工程任务和研究数学上会保留同等效果。值得学习的是：领域数据、可执行/人工反馈和候选修正循环如何互相放大，而非把分数简单归因于参数规模或 SFT。

### Holo4 开放计算机操作模型与轨迹，评测仍需同口径复跑

**质量：B｜重要性：高｜此前漏报，原始发布：2026-09-28。** [H Company 原始技术说明](https://hcompany.ai/newsroom/holo4)公开了 Holo4 27B dense 与 35B-A3B MoE 的[权重](https://huggingface.co/collections/Hcompany/holo4)及[公开基准逐步轨迹](https://trajectories.hcompany.ai/)。模型用 GUI、代码、MCP/API 混合操作；训练链从产品文档和真实软件构造约 1 万项带状态验证器的任务，用约 1270 亿 token 做 SFT，再分别训练桌面/网页与终端/API 两个 LoRA 强化学习专家，等权合并。任务验证器需拒绝未改动的初始状态和近似错误状态、接受目标状态，体现了“生成任务—可执行验证—失败审计”的可复用数据工程方法。作者还把长任务中的记忆压缩、同机 shell、步数与视觉服务缺陷列为 harness 改进；这提醒读者模型能力和执行环境共同决定成绩。

**现有证据可用于试验，不能直接当作统一排名。** 团队自测 Holo4 27B 在 OSWorld 2.0 的平均部分得分为 61.7%，优于其列出的 Qwen3.8 27B 48.0%，仍低于所引 Opus 5.5 的 81.8%；发布页明确指出这些分数涉及不同任务子集、harness 和 effort。AutomationBench 的 600 项公开集里有 480 项与训练数据收集所在拆分重合，私有集尚未评测；因此该数字尤其不能等同于独立泛化证据。开放权重和运行轨迹提高了可审计性，适合对 GUI/工具混合 Agent 做同环境复跑和错误归因；目前更值得学习的是任务构造与验证链，而非把自报价格/分数当成采购结论。

# 系统与编译器进展

### IBM Spyre 作为原生 PyTorch 设备：从二次建图转为有序操作队列

**质量：A｜重要性：中｜原始发布：2026-10-08。** [PyTorch 原始技术文章](https://pytorch.org/blog/building-spyre-as-a-native-pytorch-device/)和[公开的 `torch-spyre` 仓库](https://github.com/torch-spyre/torch-spyre)给出完整接入链。Spyre 是数据流式推理加速器，芯片以 32 个核心、每核 2 MB scratchpad 与最高 128 GB LPDDR5 组织存储，无法简单套用 GPU kernel 的执行模型。团队通过 `PrivateUse1` 赋予 `device="spyre"` 真正的 PyTorch 设备身份，以 allocator 管理驻留张量的生命周期，让 FX 图留在 Inductor 编译路径，并将编译产物转换成可复用的启动计划。调用时只向有序队列提交主机准备、搬运、计算与同步等带类型的操作；eager 注册算子也复用同一套分解、编译与启动链，而非另建一条手写运行时。

**关键设计与效果。** 旧实现每次调用都要把已编译程序再次翻译为运行时图、读盘反序列化、拼接张量参数后再解析；PyTorch 同时无法把自定义驻留状态识别为普通设备张量。新路径把这些工作前移到编译产物首次加载时，调用阶段只修补地址并排队执行。Spyre 的内存区域句柄预算、有限地址窗口又迫使 allocator 在少量区域内管理多个张量，并在启动时对程序地址做修补；独立的主机准备和设备计算则借助 stream 与事件建立必要依赖。官方在 Granite 3.3 8B、batch 1、序列长 1024 的对照中称，仅移除传输路径的二次建图，prefill / decode 分别改善 9.9% / 13.6%；连计算派发一起改造后分别达到 1.7 倍 / 2.4 倍。数字来自同一团队的特定模型与硬件配置，展示的是整个 runtime 重构收益，不能解释成 `PrivateUse1` 本身的通用加速。

**可复用经验与边界。** 对其他加速器后端，最有价值的检查顺序是：框架是否真的拥有设备张量存储、编译图是否只在恰当边界被解释一次、启动时哪些元数据必须绑定，以及事件是否在实际调度层保证跨流先后关系。公开仓库包含 C++/Python 实现、文档、示例与测试，也接入 PyTorch 跨仓库 CI；但目前构建仍需 IBM Spyre 软件栈的开发版本，外部独立复跑门槛高。文章明确指出算子覆盖、profiling、分布式 collective 与模型内核质量仍需后端继续实现，用户自建事件的公开 PyTorch 接口也尚未等同于运行时内部依赖机制。因此应把这篇文章视为有实测的设备抽象与执行链案例，而非“任意 PyTorch 模型无需适配即可高效运行”的保证。

# 科研进展

### ThinkingBox：用最终数据库状态与重复运行检验 Agent

**质量：A｜重要性：高｜证据成熟度：M1｜此前漏报，原始发布：2026-10-03。** [Microsoft 与 Hugging Face 的原始技术文章](https://huggingface.co/blog/microsoft/thinkingbox)、[论文](https://arxiv.org/abs/2608.19741)和[可运行基准数据](https://github.com/microsoft/thinkingbox-data)针对一种常见评测错位：Agent 最后声称完成、工具调用也正常返回，但客户记录仍被写错。507 个有状态业务任务为每次尝试初始化隔离的后端和 MCP 工具会话，以可执行断言检查最终字段及副作用；同一任务独立运行 20 次，分别报告单次通过率、20 次内至少成功一次，以及实际 20/20 全部成功的任务比例。后两者的问题不同：前者衡量“能否碰巧做到”，后者衡量可重复依赖性。

**为什么这比普通榜单更有信息量。** 在 12 个模型、121,680 次有效试验的共同集合中，79,853 次未通过可执行检查；这些失败尝试里 67.24% 仍正常结束、调用过修改状态的工具，而且没有最终工具错误。失败中错误字段、意外额外副作用、缺失必要副作用的比例分别为 77.61%、43.30%、25.36%，彼此可以重叠。结果显示，检查轨迹表面流畅程度会系统性高估完成质量。按模型划分的 20/20 成绩又显示单次成功便宜的模型未必是可重复完成任务最省成本的选择。文中的“约八成失败属工具处理”是基于可观察失败标签的归因，不等于证明底层模型推理无关。

**复现与边界。** 文章给出固定数据 release、框架提交与 bundle hash 的运行方式；[OpenEnv 适配器](https://github.com/huggingface/OpenEnv)和 ThinkingBox CLI 可启动环境，需自行准备模型端点、Typesense、Docker 等组件。系统错误在官方统计中按失败处理，但真实业务流程还受权限、长时状态、异常恢复与外部服务变化影响；507 项任务不能代表所有 Agent 应用。最可迁移的实践是在自己的工作流中定义“完成后必须成立的数据库状态与禁止出现的副作用”，从统一初始状态重复运行，并报告明确的 every-of-k 指标。训练代码仍标为后续工作，当前主要价值是评测环境和可执行验证契约。

# 本期最值得关注

**先复用 ThinkingBox 的验证契约，再研究 Nemotron 的专门化循环。** [ThinkingBox](https://huggingface.co/blog/microsoft/thinkingbox)最直接改变 Agent 工程判断：把输出文案、工具返回与实际后端结果分开，重复运行同一任务；适合先在自己的代码与数据工作流里落地。随后看[Nemotron 的训练与推理材料](https://huggingface.co/blog/nvidia/nemotron-ioi-and-imo-2026)，区分微调、验证器/执行反馈和测试时搜索的贡献。关注异构运行时的读者可再用[PyTorch 的 Spyre 案例](https://pytorch.org/blog/building-spyre-as-a-native-pytorch-device/)核对旧路径与新路径的行为链。
