## Part 1/3

# 今日总览

今天优先看两条系统设计线索：**Humming 把量化格式与执行配置分开，Specter 把推测解码的路由信息用于提前搬运专家权重。** 前者适合理解可维护的低比特内核架构，后者适合理解缓存、异步 I/O 与正确性边界如何共同决定端到端收益。

Nemotron 3.5 则值得从检索链整体看：保留既有文本表示、加入视觉证据，并把重排收益与总计算成本分开衡量。Flint 的单卡低延迟实现也值得拆解：减少 kernel 发射的同时保留参考实现的舍入语义。OpenShell 0.1.5 则展示了另一类系统难题——收紧安全边界时，旧策略、DNS 和持久化行为如何一起变化。

# 业界进展

### Nemotron 3.5：让视觉文档进入既有检索链，同时区分模型与流水线成本

**质量：A｜重要性：高｜Personal Utility：高｜Evidence Maturity：M1。** NVIDIA 于 2026-10-21 发布整套技术介绍，包含 Embed 8B/1B、1B NVFP4、8B Rerank 与 631M Parse。资产并非全部当天首发：8B Embed 模型卡标注 10-20，Parse 标注 10-17。核心增量是把页面图像、文字和混合文档接入检索与重排，并公开权重及部署路径。[发布介绍](https://huggingface.co/blog/nvidia/nemotron-retriever-world-class-agentic-retrieval)

最值得注意的是兼容性设计：[8B 模型卡](https://huggingface.co/nvidia/Nemotron-3.5-Embed-8B-BF16)说明语言部分沿用 Nemotron 3 Embed 并保持冻结，仅训练视觉编码器和投影层，因此对应 BF16 版本保留相同文本嵌入空间。旧文本索引有复用基础；这是新增视觉能力，不能解释成文本检索全面变强。实际迁移仍应固定预处理、向量维度与归一化；8B 默认输出 4096 维，截到 1024/512 维后要重新 L2 归一化，查询端只接受文本。

作者在 ViDoRe v3.1 报告 8B、1B 分别为 61.17、58.38 nDCG@10。固定 Agent、工具、任务集和语料，仅改变检索配置的实验中，加入重排使 Agent 推理 token 降低约 13%～14%；该统计没有涵盖重排服务本身的 GPU 开销，不能直接换算成总成本节省。训练包含合成数据，现有报告也尚非独立复现。

[NVFP4 模型卡](https://huggingface.co/nvidia/Nemotron-3.5-Embed-1B-NVFP4)明确要求支持该精度的 Blackwell 硬件及 vLLM；需要 Transformers 的用户应选 BF16。其单独 ViDoRe V3 对照中，图文联合输入得分为 58.71，对应 BF16 为 58.82；不要把它与 v3.1 分数直接拼表。低精度索引是否仍满足自己的召回要求，需要单独检查，不能沿用 BF16 的相同向量结论。

[Parse 模型卡](https://huggingface.co/nvidia/Nemotron-3.5-Parse)采用视觉编码器与十层 mBART 解码器，输出结构类别、位置与阅读顺序，并包含供 vLLM 使用的一步 MTP 头。它在 H100 上的取舍很明确：单遍为 72.74 分、16.1 页/秒；三遍区域细化为 75.20 分、10.5 页/秒，最高质量与最高速度不是同一配置。权重采用 OpenMDW-1.1，部署时还应分别核对模型与依赖许可。

**建议投入：立即学习（1～3 小时）。** 先对一批含表格和图表的自有文档，比较文字、页面图像、图文联合三种索引，再分别加入 Parse 和 Rerank。固定查询、相关性标注与候选数，同时记录召回、Agent token、重排耗时和总 GPU 时间；可学会判断收益究竟来自更好的表示、文档结构还是额外推理计算。

# 系统与编译器进展

### Flint 的 vLLM 实现：以参考数值语义约束小 batch 优化

**质量：A｜重要性：高｜Personal Utility：高｜发布：2026-10-21｜Evidence Maturity：M1。** [vLLM 技术文](https://vllm.ai/blog/2026-10-21-flint)提供专用 Docker 镜像；模型接入 [PR #62938](https://github.com/vllm-project/vllm/pull/62938)目前仍为 Open，不能视作稳定版主线已经交付。优化重点是单 Blackwell、TP=1、小 batch 解码；其他配置回到标准层。

Flint 是 40B 总参数、约 2.5B 激活参数的 MoE，49 层中 35 层使用局部窗口，14 层保留全上下文注意力。NVFP4 检查点以 GGUF 存储，加载时重排为执行布局，实际走 **W4A16、BF16 激活与 KV**；不能把文件名直接理解成全链路 FP4。

原标准层实现每次 forward 发射 1,096 个 kernel。新路径融合 Q/K 归一化、RoPE 和 KV 写入，对小 batch 采用专家索引 GEMV，并以 programmatic dependent launch 串接每 MoE 层七个 kernel，使前向发射数降至 346。各阶段同时遵循参考实现的舍入位置，避免把融合带来的数值变化误当成无损替换。

作者在单 GB200、100K 上下文的 batch-1 测量中，NVFP4 forward 从 4.81 ms 降至 1.78 ms；完整服务解码为约 2.06 ms/token，即约 485 tokens/s。前者是前向算子时间，后者还包含 LM head 和采样。PR 给出固定 tree 的测试、GSM8K 与工具调用检查；数值比较采用 KL 等容差标准，不能改称逐位一致，也没有独立多租户服务验证。

**建议投入：立即学习（1～3 小时）。** 从 PR 的 `vllm/models/flint/` 与 `tests/models/flint/` 配对阅读。学完应能解释：为什么大 batch 的 GEMM 路径未必适合单请求、如何减少 launch 开销，以及优化后怎样继续检查参考数值行为。复跑应固定镜像和 revision，并分别计量 forward、采样及请求端延迟。

### OpenShell 0.1.5：安全策略收紧包含可见的兼容性变化

**增量质量：A｜重要性：中｜Personal Utility：高｜Evidence Maturity：M1｜发布：2026-10-21 北京时间。** [正式版说明](https://github.com/NVIDIA/OpenShell/releases/tag/v0.1.5)新增 Kubernetes pod annotation/label 的操作员 allowlist，并拒绝调用方使用保留的内部 annotation 前缀。直接 API/SDK 设置模板元数据、包括超时沙箱恢复，可能受影响；CLI 普通 metadata label 不等同这条路径。

[DNS 修正 PR](https://github.com/NVIDIA/OpenShell/pull/4602)将按主机名授权的解析绑定到 supervisor 控制的 DNS；沙箱自定义别名需要独立 IP 限制或可信网关 pin。这会改变依赖 `/etc/hosts` 或 Kubernetes `hostAliases` 的既有策略，升级前应核对实际连接行为。另有 broker 无法验证描述符时拒绝操作、MicroVM 关闭前刷新文件系统等修复，分别涉及授权失败路径与最近写入的持久化。

策略配置推送是显式选项，发布说明称传播约 100 ms，旧 polling 仍默认；这不是安全决策本身的总延迟承诺。证据来自实现、回归测试和发布记录，项目整体仍缺独立安全审计。**建议投入：立即学习（1～3 小时）。** 重点对照旧策略与新 DNS/元数据规则，构造允许、拒绝、别名解析和恢复四类用例；可学习如何把安全修正、兼容性与恢复语义一并评估。

### TorchNeuron profiling：把框架调度、运行时与硬件执行对齐

**质量：A｜重要性：中｜Personal Utility：高｜发布：2026-10-21。** Amazon 工程师的[教程](https://huggingface.co/blog/amazon/profiling-torchneuron-part-1)提供 RMSNorm 示例，说明如何同时启用 PyTorch `PrivateUse1` 与 Neuron 运行时、设备 trace，再沿 dispatch → `nrta_execute_schedule` → `nc_exec_running` 查找间隙。循环内必须同步设备，避免导出时设备尚未完成而出现空计时。

相同 BF16 `[4,512]` 输入下，作者展示逐算子、内置融合与 `torch.compile(backend='neuron')` 三条路径：设备时间约 2355、403、376 微秒。这里只记录一个预热后的 active iteration，不能外推整模型加速或生产尾延迟；还需分别检查 CPU 调度与同步成本。

**建议投入：立即学习（1～3 小时）。** 先按表格定位热点，再对照完整 trace 判断是否由多次发射和中间张量造成。即使暂不使用 Trainium，这条从框架事件追到硬件执行的证据链，也适合迁移到其他加速器后端的 profiling。

### Humming：用统一表示承接量化差异，再为负载选择执行路径

**质量：A｜重要性：高｜Personal Utility：极高｜Evidence Maturity：M1｜技术发布：2026-10-21。** [官方仓库](https://github.com/vllm-project/humming)提供 Apache-2.0 核心实现、配置、测试和 benchmark 目录；Humming 此前已出现在其他内核的比较中，本次是完整架构与性能说明，不能称为今天才首次存在。

它把格式差异集中到量化表示，再分别描述层、计算选项和调优配置。[配置接口](https://github.com/vllm-project/humming/blob/main/humming/config/__init__.py)区分 `LayerConfig`、`ComputeConfig`、`TuningConfig`；[HummingLayer](https://github.com/vllm-project/humming/blob/main/humming/layer.py)将格式转换与运行时 forward 分开，执行前须先 `transform()`。这样可沿同一调用链追踪数值语义、权重重排与调度选择，适合学习编译专化如何控制组合复杂度。

[技术文](https://vllm.ai/blog/2026-10-21-humming)的关键对照是八张 H20、TP=8 的 DeepSeek-V4.1-Flash：保持 MXFP4 权重，MoE 从 Marlin W4A16 改为 Humming W4A8，作者报告吞吐增加约 14%～43%。**激活精度也由 BF16 改为 tokenwise FP8**，因此收益包含计算格式变化，仍需同任务质量核验。微基准已预热并使用冷 L2，不能直接代替服务尾延迟；尚缺独立复跑。

支持矩阵按设备和激活类型限定组合，并非所有 SM75+ 设备都能走全部精度路径。当前以设备启发式选择配置，自动搜索仍列为后续计划。官方说明 vLLM 0.29.0 起 CUDA 安装已包含依赖，可分别用 `--linear-backend humming`、`--moe-backend humming` 选择后端；普通后端选择与兼容量化加载选项不是同一用途。

**建议投入：深入学习（半天～2 天）。** 先从 README 的单层示例走通“权重载入→转换→执行”，阅读 `humming/schema/`、`transform.py`、`config/` 与 `jit/`。自己的实验先固定权重和激活精度，对比原有后端，再单独改变激活类型；分别记录正确性、冷编译和热执行时间。学完可更清楚地设计量化 IR 与后端接口，并判断性能差异来自格式、布局还是执行策略。

# 科研进展

### Specter：利用 draft 路由提前搬运专家，保留目标验证边界

**质量：A｜重要性：中｜Personal Utility：高｜Evidence Maturity：M1。** [论文](https://arxiv.org/abs/2511.14102)初版发布于 2025-11-18，本次关注的是 **2026-10-20 的 v2 与公开 artifact**，不是把旧论文重新包装成首发。针对显存不足的 MoE，量化 draft 一边提出 token，一边预测目标专家工作集，使 PCIe 搬运与计算重叠；目标模型继续负责验证。

[设计文档](https://github.com/wwwwwf/specter_asplos/blob/main/docs/design.md)把执行拆成推测控制、预测 I/O 和计算引擎。值得追踪的两个不变量是：验证后仅保留已接受边界的目标 KV；缓存槽不能在专家排队或使用期间被覆盖。专家按驻留状态重排执行，再散射回 token 顺序，把预测失误处理与计算正确性分开。

[正文实验](https://arxiv.org/html/2511.14102v2)使用 A100 40GB、Xeon 主机及 PCIe 4.0，覆盖三种 MoE 和五类数据；相对更接近的方法 SpecMoEOff，单请求 TPOT 加速平均约 1.50 倍、最高 1.88 倍。论文另有批量实验，但公开复现包明确以 batch 1 为目标，不能把全部论文结果都视为包内一键复现范围。结果仍是作者测量，缺跨硬件独立验证。

[复现说明](https://github.com/wwwwwf/specter_asplos)给出依赖锁定、资产哈希、资源检查及高/低驻留配置。默认 DeepSeek 实验每数据集五个输入、三次重复，生成 128 tokens；它能检查指定协议，不能代表长上下文或生产并发分布。完整准备还需约 200GB 磁盘及固定 CUDA/PyTorch 环境。

**建议投入：立即学习（1～3 小时）。** 先读 `state.py`、`expert_cache.py` 和 `overlap_optimizer.py`，画出接受边界、槽所有权与 CUDA event 的依赖；有匹配硬件时再从 `benchmarks.run_ae` 默认实验开始。当前价值在于把推测执行、共享状态和 I/O 重叠放进一条可验证执行链，帮助判断“预测准确”何时才能转化为真实延迟收益。
