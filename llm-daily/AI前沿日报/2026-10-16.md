# 业界进展

### Nemotron 3.5 Super VL：开放多模态 MoE 的价值在“模型、精度与服务路径”一并交付

**质量：A｜重要性：高｜Personal Utility：高｜原始发布：2026-10-15。** [NVIDIA 官方发布](https://developer.nvidia.com/blog/nvidia-nemotron-3-5-super-vl-powers-specialized-agents-with-multimodal-reasoning/)及[79 页技术报告](https://research.nvidia.com/labs/nemotron/files/NVIDIA-Nemotron-3.5-Super-and-Lightning-Technical-Report.pdf)确认：Super VL 是约 **120B 总参数、12B 激活参数**的混合 Mamba/Transformer MoE，面向文本、图像、文档和视频输入及文本输出；提供最高 **100 万 token**上下文。发布同时提供基础、后训练和 NVFP4 权重、训练资料与部署配方，因此团队能检查模型本身，并尝试在自己的 Agent 任务中复跑。

**技术增量。** 一条模型路径同时处理代码/工具任务与视觉证据，减少“文字模型＋视觉模型”之间的转交；后训练包含对 Nemotron 3 Ultra 的蒸馏和多教师引导。服务侧叠加 MTP、LiLiCorr draft、按组件选择精度的 NVFP4 量化感知蒸馏，以及跨 Agent 回合保存注意力 KV 与 Mamba 状态。它们分别作用于验证步数、模型带宽和重复前缀计算，不能合并成一个没有条件的“5 倍提速”。尤其 NVIDIA 所报 **16 张 B200、每用户至少 50 token/s 时可服务用户数最高 8 倍、首 token 延迟降低 85%**，来自 Dynamo 的会话亲和路由与缓存卸载组合，不是单模型对单模型的速度比；LiLiCorr 在 DGX Spark 上“最高 2.3 倍”也只对应文中的解码配置。

**证据与边界。** 权重、技术报告和部分部署配方使架构与部署主张可查；Hermes Bench 和 LangChain Evals 上 Super VL 高于 Nemotron 3 Ultra，说明其特定 Agent 测试表现，但不同 harness、提示与预算不能直接推成全面胜出。厂商文章中的合作方成本、延迟和准确率数字分别来自不同业务与后训练设置，不能横向拼成同一基准。权重开放也不等于无限制许可；采用前需核对[模型卡](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Super-VL-120B-A12B-NVFP4)的许可、显存需求与目标框架支持。**投入建议：深入学习（半天）。** 先读报告的训练、评测和推理附录，再在固定代码/视觉 Agent 任务上同时量正确率、端到端耗时、显存、并发和成本；分别打开量化、推测解码与缓存，找出收益来自哪一层。

### Apertus 1.5：新发布的是技术说明，完整开放资产使多模态训练路径可检查

**质量：A｜重要性：中｜Personal Utility：中｜说明发布：2026-10-15；权重发布：2026-07-24。** Swiss AI 的[原团队发布说明](https://huggingface.co/blog/swiss-ai/apertus-v15-release-notes)和[技术报告](https://arxiv.org/abs/2610.15542)详述既有 8B/70B 权重：持续预训练分别增加约 4T/2T token，采用离散图像与音频 token 的早融合路径，512×512 图像约占 1024 token、音频约每秒 40 token，不新增独立视觉编码器；上下文扩至 262k，并增加推理模式、长上下文训练和后训练阶段。模型只输出文本，语音理解仍属实验能力。

它值得读的原因是公开权重、数据来源、训练细节与评测卡能让研究者追查模型形成过程；“结构不变、按文本速度训练”是训练结构上的表述，不保证多模态任务的实际 token 成本与延迟不变。新文章也不能写成今日新模型发布。**投入建议：选择性学习（1～2 小时）。** 若研究开放训练或离散多模态 token，核对技术报告中的模态消融、长上下文评测和数据治理；若只为最强 Agent 选型，优先看真实任务对照。

# 系统与编译器进展

### Hugging Face BERT normalizer：瓶颈定位清楚，但“50 倍”跨了两个基线

**质量：A｜重要性：高｜Personal Utility：高｜原始发布：2026-10-15；代码仍在待合并 PR。** Hugging Face 工程师在[技术分析](https://huggingface.co/blog/huggingface/tokenmaxxing-bert)、[实现 PR](https://github.com/huggingface/tokenizers/pull/2508)和[复现代码](https://github.com/SBrandeis/tokenmaxxing-bert-reproducer)中，把 BERT 编码时间约 **88%** 的 normalizer 热点拆开：用 ASCII 快速路径跳过常见字符，以 256 个码点为页缓存 Unicode 是否可能变化的判断，并在输入本来规范化时延迟分配和复制。改动是保持 token ID 相同的实现优化，并非换词表或近似分词。

**如何读数字。** `tokenizers` 0.23 到 1.0 候选版本已使该测试约快 **8.6 倍**；本文 PR 在新版主线上再提高最多 **5.7 倍**，合计约 **50 倍**是相对旧 0.23，不是相对当前主线。某英文样本的完整编码吞吐从主线 **23 MB/s** 到分支 **151 MB/s**；作者在两台 EPYC 和一台 Xeon 上固定单线程、交替测量，并公开复现方法。收益强依赖字符分布：俄语、希腊语、阿拉伯语约提升 2.2～3.2 倍，中文 BERT 编码未见收益，部分中文和极短输入反而回退。**投入建议：深入学习（2～3 小时）。** 读 flamegraph 与各语种矩阵，再用自己检索/重排链路的真实文本长度和中英比例做端到端基准；PR 合并并发版后再把数字写进容量计划。

### vLLM push 式 KV 传输：将目的端准备与 prefill 重叠，而非加快 RDMA 本身

**质量：A｜重要性：高｜Personal Utility：高｜此前漏报，原始发布于 2026-10-14。** [vLLM/AWS/Mistral 的技术文章](https://vllm.ai/blog/2026-10-14-nixl-push-connector)给出已实现的 `NixlPushConnector` 与完整复现实验。原 pull 路径在 prefill 完成后才由路由器转发元数据、decode 端分配目标块并发起 READ，几步串行压在首 token 关键路径上。新路径让 decode 提前登记目标块，prefill 与登记就绪后由后台线程发起 NIXL WRITE；完成通知到齐才允许 decode，且处理重试请求和不同块布局。优化来自**计算与准备重叠、把描述符工作移出 decode 主循环**，传输网络仍是 NIXL/EFA。

在 Qwen3-32B、两台各 8×H200 的 P5en、1P1D、关闭 decode 前缀缓存、1k～16k 输入和 1～8 QPS 的作者实验中，高负载 16k 场景 TTFT 约 **1744→540 ms**，TPOT 约 **10.4→7 ms**；短输入和轻负载几乎无差异。关闭前缀缓存是为保证每次确实发生完整 KV 转移，并非典型生产配置。Push 需要更早锁定 decode 节点，牺牲 prefill 结束后再按负载路由的灵活性，也暂不适用于需要双向 KV 的多轮场景。**投入建议：深入学习（2～3 小时）。** 若已有 P/D 分离部署，按自己的前缀缓存命中率、路由策略、并发和长提示比例复跑；它与 10 月 12 日报道的双向 KV 属于不同取舍，不能直接相加提速。

### vLLM 自适应验证：用在线接受率校准替代专门训练的置信度头

**质量：A｜重要性：高｜Personal Utility：高｜此前漏报，原始发布于 2026-10-14。** [vLLM 实现分析](https://vllm.ai/blog/2026-10-14-adaptive-verification-online-estimator)和[合并 PR](https://github.com/vllm-project/vllm/pull/52228)把 Adaptive Verification 扩展到缺少 confidence head 的 EAGLE、MTP、DFlash 等 draft 模型。它从 draft 分布的最大概率取 log-odds，在线用目标模型验证时本已产生的接受/拒绝标签拟合逻辑回归；K 个 draft 位置只需一个共享斜率和 K 个截距。准确的接受率校准决定哪些低收益候选可在 target forward 前裁剪；直接把 draft 自身概率当接受率会高估，作者样本的校准误差 ECE **0.0736→0.0100**。

**关键约束。** 输入特征使用分布最大概率而非被采样 token 的概率，是为了避免按采样结果选择性裁剪造成输出分布偏移；接受率模型只控制验证预算，最终 token 仍由目标模型的正确验证流程决定。收益集中在大 batch、target 验证计算昂贵的条件，且需要支持变长验证的 attention backend；自回归 draft 如 MTP/EAGLE 因被裁掉的 token 也已付出生成成本，收益通常低于 DFlash/DSpark。文章给出多模型组合的服务对照，但最佳固定 draft 长度在某些条件下仍可能更快。**投入建议：深入学习（2～3 小时）。** 对本地模型配对先比较准确率不变前提下的吞吐、TPOT、GPU 利用率和热身收敛，再决定是否开启 AV，不用单个 ECE 值替代端到端测试。

### ClangIR：默认构建前先算 MLIR 依赖的代价

**质量：A｜重要性：高｜Personal Utility：中高｜此前漏报，原始发布于 2026-10-11。** [MaskRay 的技术审查](https://maskray.me/blog/clangir-and-the-cost-of-mlir)对照 ClangIR 团队进展、LLVM 构建数据和本地测量。讨论中的决定是让 CIR **随 Clang 默认构建**，当前常规代码生成仍走既有 CodeGen，`-fclangir` 仍需显式启用；不能表述为所有 C/C++ 编译立即换成 MLIR 路径。ClangIR 已能完成部分自举和测试，但调试信息、sanitizer、非 x86 等覆盖与原本期望的优化收益仍在推进。

**成本在哪。** 纳入 CIR/MLIR 后，作者引用的编译时间跟踪显示构建文件累计编译工作量约增 **48%**；触碰 `DenseMap.h` 等公共头文件的增量重编译累计时间约增 **49%**，构建峰值 RSS 约增 **40%**（约 1 GiB）。在不同机器、链接模式与削减 MLIR 依赖的阶段，`ninja clang` 墙钟开销差异很大，不能把这些 CPU 工作量数字解释成每次完整构建都恰好慢一半；某些多核墙钟结果较小也会掩盖依赖图和长尾编译单元。文章是作者参与讨论后的工程测量与判断，尚非跨所有平台的独立标准基准。**投入建议：定向学习（1～2 小时）。** 关注构建配置、增量迭代和二进制体积的主路径成本；如果开发 LLVM/Clang，在自己 CI 与开发机上分别测 clean build、公共头变更、RSS 和 `-fclangir` 功能覆盖，再评价默认构建决策。
