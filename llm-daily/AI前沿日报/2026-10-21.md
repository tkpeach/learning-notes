# 今日总览

- **今天优先读编译器与运行时之间的契约。** TorchTPU 将 PyTorch 的 eager、视图和分布式语义接到 XLA；Spyre 则把既定的核间分工逐步降为显式数据流。这两条路径都适合用来理解异构后端如何保留上层语义。
- **vLLM 弹性扩容的关键是保留可重放状态。** 后台准备配合 NIXL EP，把特定负载的服务暂停压到约一秒，但扩容准备本身仍需几十秒；不要混淆停顿和总耗时。
- **Mac 上值得关注的是具体算子路径。** MPS 2.15 的技术复盘解释了 grouped matmul、padding 和 stream 生命周期；当前文章提供的是候选版试用路径，2.16 的预告另算。

# 业界进展

### MultiLangBench：用统一数据库接口评价跨语言实现，迁移则检查可观察行为

**质量：B｜重要性：高｜Personal Utility：高｜此前漏报，发布：2026-10-19。** [OpenAI 正文](https://openai.com/index/low-resource-programming-languages/)公开两类评测：在 20 种语言中实现 SQLite 兼容引擎，以及把 COBOL 程序迁到 C++、Java、Kotlin、Python 或 Rust。前者比较从零构建，后者要求隐藏测试的可观察输出逐字节一致，能识别舍入、缺失记录等业务语义偏差。

官方自测中，MultiLangBench 的平均测试通过率由 GPT-5.6 Sol 的 26.8% 升至 GPT-6 Astra 的 87.4%；COBOL 迁移中，GPT-6.1 Sol 在低推理强度下为 86.6%，对照为 5.4%。这是两个不同任务及指标，不能合并成通用软件工程成功率；成本数字也限定于官方使用的 API 预算和评测设置。

[开源评测](https://github.com/openai/MultiLangBench)提供真实测试实体：从约 5.1 万项 SQLite TCL 测试转成约 2.4 万项数据库状态测试，常规运行建议使用哈希前缀选出的 **272 项**；隔离环境必须移除已有 SQLite，禁止联网，最终评分在环境外用 SQLite 3.40.1 检查输出数据库。它验证的是被测试的数据库内容，不能据此认定实现了完整 SQLite 行为、并发协议或生产可靠性，也尚缺独立跨 harness 复跑。

**建议投入：立即学习（1～3 小时）。** 优先读测试转换与隔离约束，挑选一个 C++/Rust 实现任务，区分“程序能运行”“输出状态相同”和“行为全面等价”。这套方法可迁移到旧系统重写：先保存已知正常实现的输入、输出和副作用，再比较新实现，而不是仅检查代码形似或测试数量。

### TorchNeuron 的原生后端代码已公开，版本固定成为实际迁移条件

**质量：B｜重要性：高｜Personal Utility：高｜10 月 19 日公告的后续交付。** [官方仓库](https://github.com/aws-neuron/torch-neuronx)现已公开代码、训练与推理示例、构建和安装说明，补齐昨天只能确认发布计划的证据。原生后端要求 PyTorch 2.14 与 `torch-neuronx==2.14.*` 等匹配依赖；仓库明确提示，更早的同名包属于原有 XLA 产品，不能仅凭包名判断执行路径。

当前 `torch.compile` 要求静态形状和连续张量，新形状会重新编译，非连续输入每次需要拷贝；`float64` 实际以 `float32` 运行，TorchAO 复合低精度类型尚未交付。**了解即可（20 分钟）**：对照 quickstart 检查 eager/compile 的输出，再核查自己的 dtype、布局和形状集合。公开安装路径提高了可验证性，独立性能与完整模型正确性仍需积累。

# 系统与编译器进展

### TorchTPU：原生 PyTorch 语义与 XLA 编译之间，多了一层可审查的运行时

**质量：A｜重要性：高｜Personal Utility：极高｜发布：2026-10-20。** [技术正文](https://pytorch.org/blog/introducing-torchtpu/)和[公开实现](https://github.com/google-pytorch/torch_tpu)展示 Google 与 Meta 合作的 TPU 后端：通过 PrivateUse1、ATen 与标准分布式接口接入，保留 eager 和 `torch.compile` 路径；底层仍借助 StableHLO/XLA、PjRT 编译和执行。相对 PyTorch/XLA 的 Lazy Tensor 接法，主要变化是将 PyTorch 的设备与执行语义放在前面；这没有消除形状、分片及硬件布局带来的调优工作。

值得深入理解的是 **Strict eager、DeferAndFuse、编译缓存与副作用边界**。默认逐算子异步执行；可选融合模式把一组操作延后到需要物化结果时编译。这样会改变临时张量和编译开销，也要求保留集合通信等副作用的顺序。[版本化文档](https://torchtpu.readthedocs.io/en/0.2.0/)把执行、内存、动态形状和分布式分别说明，适合对照源码阅读，而不只看设备名从 `cuda` 改为 `tpu` 的示例。

**证据需要分层。** 团队报告 4,917 个模型的无崩溃通过率为 98%；另一个架构代表子集有 638/657 通过数值标准。前一项包含合成权重的 smoke/lowering 检查，后一项也使用容差，不能把两者表述为全部模型已严格等价。大规模训练数据主要为作者测量；首次编译、拓扑与精度模式会影响实际成本。TPU 每设备的进程访问约束也意味着 RL 训练和推理共置不能直接照搬 GPU 方案。

[vLLM TorchTPU](https://vllm.ai/blog/2026-10-20-vllm-torchtpu)把这条路径接成 out-of-tree plugin，复用原有调度器、KV 管理器和 API，硬件专用 Pallas kernel 位于下层。插件要求 Python 3.12，推荐 v7x，其他列出的 TPU 代际仍为实验支持；首次启动的图编译可能持续数分钟。它给出了部署路径，尚不能由“支持某模型”推断所有量化、并行和缓存组合都具有相同性能。

**建议投入：深入学习（半天～1 天）。** 先读执行模式与内存模型，再追踪一个 ATen 操作到 StableHLO、物化及缓存命中的过程；补看集合通信如何保持跨 rank 顺序。有 TPU 条件时固定小模型、输入形状与精度，分别测冷编译、热运行和数值偏差。学完能更清楚地区分框架接入、编译器优化和运行时调度分别解决什么问题。

### vLLM Elastic EP：缩短服务停顿，依赖通信和 CUDA Graph 地址保持稳定

**质量：A｜重要性：高｜Personal Utility：高｜此前漏报，发布：2026-10-19。** [原团队技术文](https://vllm.ai/blog/2026-10-19-elastic-ep-near-zero-downtime)把拓扑变更拆成后台准备和短暂提交：旧 worker 继续服务，新 worker 接收权重、预热并捕获图；提交时暂停调度，激活准备好的拓扑。仅将初始化移到后台还不够，重建通信缓冲和 CUDA Graph 仍会产生长停顿。

NIXL EP 在原通信实例中增减成员，保留图可见的缓冲、指针与启动参数，通过设备状态更新成员关系；vLLM 同时保留专家计算对象和路由存储。新 worker 预热时屏蔽远端成员，避免要求正在服务的 worker 陪跑。这里的可迁移经验是：后台准备是否有用，取决于提交后既有执行产物仍满足哪些不变量。

作者用 DeepSeek V4 Pro、GB200、TP=1、16↔20 GPU 比较三种配置：阻塞重配置的扩容停顿 **99.62 秒**，仅异步准备为 **58.04 秒**，加图复用后为 **0.82 秒**；对应完整扩容仍需 **92.34 秒**。权重预下载、编译缓存已热；缩容停顿为 1.96 秒。11,391 请求回放与数值检查支持这个指定场景，尚缺独立跨拓扑验证。文章说的 near-zero 也没有消除控制面、准备资源和失败恢复成本。

[v0.30.0 中的测试](https://github.com/vllm-project/vllm/blob/v0.30.0/tests/distributed/test_elastic_ep.py)包含 `cuda_graphs_heavy_nixl_ep`、有流量扩缩容以及变更前后准确率检查，足以把设计落到可审查代码。**建议投入：深入学习（半天）。** 先画出准备、提交和失败三条状态路径，列出图捕获的地址与布局不变量，再读四 GPU 测试。实践时同时记录服务暂停、总耗时、额外显存及取消后的资源回收，不能只比较一个秒数。

### MPS 2.15：消除 CPU 同步和驱动内存膨胀，比套用吞吐倍数更值得学

**质量：A｜重要性：中｜Personal Utility：高｜技术复盘发布：2026-10-20；相关 PR 此前已合入。** [Hugging Face PyTorch 团队文章](https://huggingface.co/blog/mps-pytorch-2-15)给出从 MPSGraph 转向专用 Metal kernel 的多项改动，当前试用说明仍指向 2.15 候选版，并要求 macOS 15+、Python 3.11+；2.16 的预览不属于本次已交付范围。

最值得读的是 [grouped matmul 实现](https://github.com/pytorch/pytorch/pull/194933)：旧路径把分组偏移读回 CPU，再逐组执行；新路径直接在 GPU 读取偏移并处理边界。由于 CPU 不知道各组长度，kernel 发射与空工作组判断也必须一起设计。dense `F.linear` 则接上已有 GEMV 路径，作者对 96 个 BF16 层形状报告约 1.23 倍几何平均收益，大层和 LM head 仍接近带宽上限。不能把小投影或 MoE 路径的收益套到全部模型。

[constant-padding 修正](https://github.com/pytorch/pytorch/pull/195368)还说明了内存指标的差别：指定 Wan2.2 tiled VAE 工作负载的驱动峰值由约 270 GiB 降至约 8 GiB，而 allocator 预留峰值约 8 GiB 基本不变；问题不等于模型张量本身需要 270 GiB。新的 stream 接口与 `record_stream` 也把异步存储寿命暴露给调用方。以上主要是贡献者测试，仍需在自己的设备和版本上验证。

**建议投入：立即学习（1～3 小时）。** 优先看 grouped-mm 的 GPU 偏移处理，再用一个小算子同时测同步后的墙钟时间、张量分配与 driver memory。学完能更准确地定位 Mac 推理中的 CPU 往返、算子选择和缓存占用；已有稳定环境可另建候选版环境做比较。

### cuTile Mamba-2：递归状态与矩阵计算分开，前向收益有明确硬件边界

**质量：A｜重要性：中｜Personal Utility：高｜此前漏报，发布：2026-10-19。** [Jane Street 与 NVIDIA 的技术正文](https://developer.nvidia.com/blog/accelerating-mamba-2-with-high-performance-forward-pass-kernels-in-nvidia-cuda-tile/)把前向分为块内衰减前缀和、跨块状态传递、输出计算三个 kernel。跨块依赖保留在每个程序实例内，独立 batch/head/state 分片并行；输出阶段融合交互矩阵、衰减、因果掩码和残差，减少中间结果落入全局内存。

优化包括转置全局内存布局以利用 TMA、交换矩阵操作数以适应 Blackwell 的 Tensor/Shared Memory 非对称，以及按形状搜索块尺寸和 occupancy。[TileGym](https://github.com/NVIDIA/TileGym)是对应实现与测试入口。作者在单 B300、cuTile 1.5.0、TileIR 13.4 等指定环境，对比 `mamba_ssm 2.3.2.post1`/Triton 3.7.1，报告前向 kernel **1.14～1.82 倍**；尚不包括反向和完整训练收益，也没有独立复跑。

**建议投入：立即学习（1～3 小时）。** 从正文的三段公式与 `chunk_cumsum` 小 kernel 开始，再读 `compute_out` 如何融合临时矩阵。能学到线性注意力并非没有串行依赖，以及数据布局、数值掩码和矩阵操作数位置怎样共同限制优化。没有 B300 时可先做公式与 IR 阅读。

### Spyre DataflowScheduler：从可检查的简单流水线逐步生成硬件合法调度

**质量：A｜重要性：中｜Evidence Maturity：M1｜Personal Utility：极高｜技术说明发布：2026-10-20。** [技术文](https://pytorch.org/blog/from-ktir-to-spyrecode-an-mlir-dataflow-backend-for-ibm-spyre/)补齐之前 Inductor 与原生设备文章之间的后端环节。Inductor 已决定布局、核间分工和 scratchpad 放置，KTIR 把这些决定作为约束交给后端；调度器负责把它们实现为流水线，不重新猜测上层映射。

在 [Apache-2.0 仓库](https://github.com/torch-spyre/dataflow-scheduler)中，核心代码、架构描述、命令行与 lit 测试形成了可学习实体。处理链从简单 load→compute→store 开始，按架构图展开合法传输路径，再构造嵌套流水、双缓冲和 corelet 并行。地址与容量约束随后落实，最终输出按引擎拆分的 DataflowIR；设备专用二进制生成位于此边界之后。显式内存放置会改变传输路径，因此必须保持绑定关系，不能当作可随意忽略的提示。

**成熟度边界很清楚。** V1 支持带广播和归约的逐元素、多核程序，团队称已在代表性 Transformer 操作上验证完整链路；矩阵乘法支持与基于成本模型的优化仍在推进。当前调度使用局部启发式，不能把“有显式循环空间”写成已经实现自动搜索，也没有足以宣称通用端到端加速的公开对照。

**建议投入：深入学习（半天～1 天）。** 按 README 固定 LLVM/MLIR `llvmorg-22.1.3`，先运行 `check-dataflow-scheduler`，再读 `ktir-to-dfir-sanity-check.mlir`，打开 `--mlir-print-ir-after-all` 跟踪一个加法如何变成合法数据流。这个学习入口可在主机上研究 IR 变换，不必先拥有 Spyre；真实设备执行则需要后续设备栈。学完能自己拆分“分工、搬运、流水与发射”四类编译责任，并为每一阶段定义可验证的输入输出契约。
