## Part 2/3

# 系统与编译器进展

### ReplaySSM：用输入回放替代逐 token 状态写回

**质量：A｜重要性：高｜Personal Utility：高｜原始论文发布：2026-10-09；技术文章发布：2026-10-12。** [NVIDIA 与 Princeton 的技术正文](https://developer.nvidia.com/blog/replayssm-rethinking-state-storage-for-faster-hybrid-model-decoding/)、[论文](https://arxiv.org/abs/2610.13778)及[研究代码](https://github.com/Johnny-Liou/ReplaySSM)把同一个瓶颈说清楚：Mamba-2、Gated DeltaNet 等层虽不用随上下文增长的 KV cache，却在每个解码步读、改、写完整递归状态；高并发时显存流量成为瓶颈，草稿 token 的推测验证还需要保存或恢复中间状态。ReplaySSM 将状态表示成一个已提交检查点和短窗口内的输入记录。普通步骤计算输出并追加输入，只在窗口填满时折叠并写回检查点，因此减少大矩阵写入；推测解码只提交接受前缀，拒绝的草稿通过移动缓冲区指针丢弃。输出计算与状态更新分开后，还能让低精度检查点负责读取、高精度检查点负责递归更新，避免每步把读路径的舍入误差重新注入状态。

**证据与口径。** 作者在 vLLM 上对四个 Mamba-2/GDN 混合模型、单张 H100 或 B300、窗口长 16 与调优后的原有 kernel 对照：batch 256 时，SSM kernel 加速 **1.46～1.80 倍**，完整 decode step 加速 **1.20～1.47 倍**；这两个数字不能混作端到端吞吐。两个约 120B 的模型在 batch 512、四个草稿 token 的测试里，相比原有推测解码吞吐为 **1.85 倍、2.10 倍**，且匹配接受长度。作者代码提供对应的 benchmark 脚本，并列出 TensorRT-LLM、vLLM、FlashInfer 的集成 PR，证据已超出概念图，但公开速度仍是作者控制的软硬件配置，尚不能外推到所有 batch、模型和框架版本。文章明确指出 batch 1 未测得加速；共享的低精度检查点在长生成中可能掉精度，须采用高低精度分离并复测质量。

**为什么现在值得学。** 这是推理系统里“改变状态表示以同时降低 I/O、回滚成本和量化误差”的可迁移范例，而非仅替换一个 CUDA kernel。建议**深入学习（半天～1 天）**：先读论文的状态展开和 output-only verification，再看[代码中的 `benchmarks/replayssm/`](https://github.com/Johnny-Liou/ReplaySSM/tree/main/benchmarks/replayssm)；若有对应 GPU，用相同模型固定 batch、窗口长、草稿接受率与输出质量，分别测 kernel、decode step 和端到端吞吐。

### LLVM lit：高并发测试调度的实测边界

**质量：A｜重要性：中｜Personal Utility：高｜发布：2026-10-12。** [LLVM 原始技术复盘](https://blog.llvm.org/posts/2026-gsoc-improving-lit/)不仅列出优化，还展示了回退和放弃的方案。lit 从 `multiprocessing.Pool` 迁往 `ProcessPoolExecutor` 时，一次性提交约 6.45 万个测试触发管道容量与锁顺序问题；将待提交任务限制为 worker 数的若干倍后，避免了这一死锁。其后在 64 核 AArch64 上，重复扫描全部 future 让 `check-llvm` 比原基线慢 56%；改为完成回调队列并加入批量派发后，作者在 64 核工作站测得 **50.7 秒→48.38 秒**。单进程 asyncio 在 `-j1` 快 **1.8～2.3 倍**，但 `-j4` 起慢 **1.5～1.9 倍**；线程池因 GIL 与子进程管理开销更慢。不同机器与测试集的秒数不能直接互比，文章价值在于对主链路的故障机制、Amdahl 上界和负结果都给出测量。建议**立即学习（1～3 小时）**：读进程池迁移、窗口化提交和高核数回归三节，用自己的测试执行器核对队列上界与完成事件复杂度。

### vLLM 的 Vera Rubin 早期支持：把硬件收益和软件优化分开看

**质量：A｜重要性：中｜Personal Utility：高｜此前漏报，原始发布：2026-10-09。** [vLLM 官方技术文章](https://vllm.ai/blog/2026-10-09-vera-rubin-preview)给出可运行的 CUDA 13.4/PyTorch 2.15 nightly 镜像、已接入的 FlashInfer kernel 和模型覆盖；还介绍通过 CUDA locality domain 将 MoE 权重按内存域分片，让 SM 更倾向读取本域 HBM。MiniMax M3 的小 token MoE 层前向在该设置下平均约 **1.2 倍**，但图中不含通信时间，不能当作整体服务收益。

**判断边界。** vLLM 团队在 AgentX 上报告 Rubin 对 GB200 的每 GPU 吞吐最高 **7.84 倍**（匹配交互性）；MLPerf VLM 路径对 GB300 最高 **3.7 倍**。它们比较的是不同整机硬件、软件栈和负载，不是 locality domain 一项优化的独立效果；夜版镜像与早期硬件也还不能替代稳定生产版本的成本、供给和故障数据。对准备评估新加速器的读者，建议**立即学习（1～3 小时）**：看文章的 locality domain 和性能配置，建立同一模型、量化、交互性与每 GPU 成本的对照表；近期没有 Rubin 硬件选择时可先了解机制，无须立即迁移。

### Miles v0.1.2：后训练后端统一与多组件作业

**质量：A｜重要性：高｜Personal Utility：高｜此前漏报，正式版发布：2026-10-09。** [官方 v0.1.2 release](https://github.com/radixark/miles/releases/tag/v0.1.2)与[核心仓库](https://github.com/radixark/miles)显示，这次并非单纯增加模型名单。此前系统由 Megatron-LM 和 FSDP 承担训练、SGLang 承担 rollout；新版本加入 torchtitan，并把 FSDP 与 torchtitan 的训练步骤、数据、损失、指标、检查点、重放和向 SGLang 的权重更新收敛到共享接口。这个变化直接影响新模型/后端接入的维护成本，也使不同后端的一致性检查更容易安排。DeepSeek-V4.1 Flash 从专用镜像和 SGLang fork 转入标准镜像；多策略作业可分别放置求解器与验证器的 trainer、rollout 队列、权重和检查点，已有 GSM8K 配置示例。

**关键新能力与边界。** 原生 Kubernetes 后端让 trainer、engine、controller 成为可独立调度的 pod，并允许部分组件重启、编排器热替换；release 标为**实验性**，Ray 仍为默认主路径。项目给出端到端恢复测试和故障注入说明，但不能由此推断多租户集群的长期可靠性。异步训练新增 `score_centering` 损失，使用采样器 top-k 概率修正旧策略 rollout 带来的梯度漂移；其收益需要在固定奖励、staleness 分布与重要性权重设置下复跑，不能仅凭功能说明认定训练更稳。作者同时补充线性/稀疏注意力 kernel、外部 SGLang 引擎连接和长响应 Agent rollout 的进程隔离。证据是代码、PR、配方与作者测试，尚缺独立多节点性能、故障恢复时间及三后端资源成本对照。

**投入建议：深入学习（半天～1 天）。** 先比较 v0.1.1 与[v0.1.2 发行说明](https://github.com/radixark/miles/releases/tag/v0.1.2)中的 backend 共享层和 Kubernetes 作业结构，再从较小模型的[官方文档](https://miles.radixark.com/)跑一条 Ray 默认路径作为基线；只有需要组件独立调度或热恢复时再试 Kubernetes，并记录 trainer/rollout 一致性、重启后的 checkpoint 与 GPU 空转时间。
