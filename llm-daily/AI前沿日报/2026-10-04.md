# 业界进展

### Claude Code mods：函数级扩展进入工具调用与权限决策链（10 月 1 日补报）

**质量：B｜重要性：高｜Personal Utility：高。** Anthropic 于 10 月 1 日[发布 mods 说明](https://claude.com/blog/claude-code-mods)，并提供[开发指南](https://claude.dev/blog/getting-started-with-claude-code-mods/)与[内置 mod 源码](https://github.com/anthropics/claude-code/tree/main/mods)。开发者可以把 TypeScript 函数打包成 Claude Code 插件，在事件处理前、后或周围运行，改写提示、拦截或重试工具调用、定制权限判断与界面；内置 `/diff` 已迁移到这一机制。相比只能在固定事件点运行的脚本钩子，mod 更适合持续维护有状态的 Agent 工作流与团队策略。

**关键边界。** mod 以 Claude Code 所在机器的权限运行，并不受沙箱隔离；插件顺序会改变拦截与结果回传行为。团队策略可让管理员管理的插件置于最外层，但管理员的加载配置仍需正确维护。公开的是扩展接口、示例和内置 mod，而非整个代理执行引擎；接口仍处早期，版本兼容和第三方插件安全尚缺独立验证。**建议投入：立即学习（1～3 小时）；从内置 `/diff` 和工具调用拦截样例入手，验证插件顺序、拒绝调用和失败回退，再决定是否用于团队策略。**

# 系统与编译器进展

### Helion 线性后端：一套 GEMM 在 vLLM 中按形状选择算法（10 月 2 日补报）

**质量：A｜重要性：高｜Personal Utility：极高。** PyTorch 与 Red Hat 10 月 2 日[公开技术分析](https://pytorch.org/blog/building-a-high-performance-and-portable-vllm-linear-backend-with-helion/)及[可运行的 vLLM fork](https://github.com/redhat-et/vllm-helion)。它没有为每个量化格式和输入形状手写独立调度规则，而是在一个 Helion GEMM 中把标准乘法、Split-K 和转置计算的 Swap-AB 作为可调选择，再针对模型实际出现的形状做提前调优。目标是 Hopper 上的动态 FP8、W8A8 INT8 与块 FP8 线性层。实现还把 Helion 限在 `num_tokens ≤ 32` 且处于 CUDA Graph 回放的小批量路径；更大的形状回退到原有 CUTLASS/DeepGEMM。这个混合策略避免了 JIT 调用和 CPU launch 开销抵消短 kernel 的收益，也限制了需要维护的配置数量。

**证据与基线。** 作者在 H100 80GB 上，对 FP8 动态和 W8A8 分别与 vLLM 默认 CUTLASS 比，对块 FP8 与 FlashInfer/DeepGEMM 比；覆盖模型使用到的算子形状后，几何平均 kernel 加速分别为 1.110×、1.178×、1.149×/1.177×。端到端以 ShareGPT 负载、单 GPU、最大并发 32、关闭前缀缓存对照默认线性后端，部分模型/量化组合吞吐提高超过 10%。算子收益和服务收益不能混为一谈：解码阶段线性层占比、CUDA Graph 命中以及批大小决定最终效果。

**部署与可迁移性。** 逐形状离线调优可耗数小时，冷启动编译与预调配置维护是实际成本；当前实现位于作者 fork，尚未并入 vLLM 主线，[上游 RFC](https://github.com/vllm-project/vllm/issues/46526)仍在讨论。标题中的“可移植”指 Helion 的设计方向，本次完整服务结果只验证了 H100，Blackwell 仅有初步 kernel 工作，不能直接外推。**建议投入：深入学习（半天～2 天）；先复现一个小批量量化模型的默认后端对照，再分别记录调优时间、冷启动、CUDA Graph 命中和端到端吞吐。**

### vLLM 分离式服务指南：ITL 尾延迟收益与 TTFT 代价同时算（9 月 29 日补报）

**质量：A｜重要性：高｜Personal Utility：极高。** vLLM 9 月 29 日的[实践指南](https://vllm.ai/blog/2026-09-29-disaggregated-serving-guide)以已发布的 v0.30.0 为基线，拆开三类工作：GPU 上的 prefill、GPU 上的 decode，以及可移到纯 CPU 节点的模板、分词和结果解析。P/D 分离让长提示预填充不再打断正在输出的流，但每个请求都要把 KV cache 从 prefill 节点转给 decode 节点；`/render` 与 `/derender` 进一步把请求变成 token ID 进出 GPU。文章还讨论多轮会话的双向 KV 传输，让 prefill 取回前一轮 decode 产生的缓存，避免重复计算整段对话。

**有说服力的正反对照。** 作者用同一台机器的两张 L40S、Qwen2.5-7B、约 8k 输入/256 输出、每档 100 个泊松到达请求、关闭前缀缓存测试。0.4 req/s 时，聚合服务的 p99 token 间隔为 169 ms，P/D 为 29 ms，说明长 prefill 确实造成 decode 尾部停顿。但两卡没有 GPU peer-to-peer，单个约 470 MB 的 KV 转移耗时约 1.3 秒；在 0.2 req/s，P/D 的中位首 token 时间为 2.2 秒，聚合路径仅 0.7 秒。文章也承认其聚合基线是一个 `data-parallel-size 2` 服务，并非最强的“两独立副本加负载均衡”方案。因此这里证明的是特定负载下 ITL 与 TTFT 的权衡，不能宣称分离式服务全面胜出。

**工程上最该先查什么。** 作者建议先看 GPU 互联和解码端 KV transfer 指标，再谈扩展 P/D；其演示 proxy 仅供开发，生产应使用更完整的调度系统。CPU 渲染层在一个约 9k token 示例中耗时约 15 ms，但流式解析若反复重放历史，CPU 工作可随输出长度急剧增长。双向 KV 路径还有正确性风险：若下一轮聊天模板丢弃上一轮的 reasoning trace，缓存与真实 token 序列会错位，当前实现可能给出错误输出。**建议投入：深入学习（半天～2 天）；以自己的 SLO 同时测 TTFT、p99 ITL 与 goodput，先验证 KV 传输，再检查多轮模板和解析开销。**

# GitHub 高价值项目洞察

### [NVlabs/cutile-rs 0.4.0](https://github.com/NVlabs/cutile-rs/releases/tag/v0.4.0)：Rust tile kernel 的调试与异步安全边界（9 月 25 日补报）

**质量：A｜重要性：中｜Evidence Maturity：M1｜Personal Utility：高。** 稳定版 0.4.0 以 CUDA 13.4 Tile IR 为基础，让优化后的 kernel 保留 Rust 源码行信息，可在 Nsight 中追到生成代码；`cuda-gdb` 能显示跨模块调用链，并可按 launch 打开 memcheck。更重要的是异步运行时修复：提交后保留 tensor 存储直到 GPU 工作完成，对跨 stream 冲突访问在入队时拒绝，补上安全 Rust 代码触发 use-after-free 的缺口。缓存命中 launch 的作者测量从 3.9 µs 降至 1.6 µs。它还加入程序化依赖启动，但这要求 CUDA 13.4、`sm_90+` 和显式 `unsafe` 等待契约；**允许提前启动并不代表生产者数据已可读取**。

**适用范围。** 作者在 DGX Spark 上跑通全套 GPU 测试，Grout 的 BF16 Qwen3-4B/32B decode 分别报告 29.5/3.7 token/s，接近该机器 LPDDR 带宽上限；这不是与 Triton 或 CUDA C++ 的公平对比。0.4.0 还含 `Global` 原子类型、`Tensor::store` token 和 raw token helper 的破坏性 API 变化，升级需逐项检查。**建议投入：立即学习（1～3 小时）；先用一条已有 kernel 验证源码行映射与 sanitizer，再评估异步生命周期和依赖启动对现有代码的影响。**
