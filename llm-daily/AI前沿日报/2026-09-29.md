# 业界进展

### Claude Opus 5.5 的长会话成本增量（9 月 24 日补报）

**质量：B｜重要性：高。** [Anthropic 原文](https://claude.com/blog/claude-opus-5-5-built-for-coding-sessions-that-use-more-context)把 9 月 22 日已发布的 Opus 5.5 从“标价更低”推进到可分析的任务成本模型：相对 Opus 5，普通输入/输出 token 单价各降 20%，缓存读取价降 60%；Claude Code 的工程改动还使未命中缓存的输入量下降逾 50%，并允许较新模型在会话中改变 effort 而不重置缓存。Anthropic 汇总的 3—9 月使用数据称，每次请求的上下文增长 2.6 倍，输入/输出 token 比由 189:1 升至 324:1。因此长任务节省费用可能主要来自缓存读取和少走的回合，而不是单看模型标价；短而确定的任务则未必得到同等比例的节省。

证据边界是这些使用分布、缓存命中与客户案例均由 Anthropic 提供，不能直接外推到另一种代码库、工具链或订阅额度。评估时应固定同一任务集，记录完整会话的缓存读/写、未命中输入、输出、工具调用、完成率和总费用；这比跨厂商单次 benchmark 或每百万 token 标价更能指导模型选择。**建议投入：了解即可（5～20 分钟），需要按量计费的长会话再做任务级对照。**

### Claude 辅助发现 ART 酶系统：有湿实验线索，功能仍待厘清（9 月 23 日补报）

**质量：B｜重要性：高。** [Anthropic 原始报告](https://www.anthropic.com/news/claude-discovers-novel-enzyme-system)描述了一个有具体产出的 AI 科研流程：约 950 个 Claude Agent 用 21 小时、2.1 亿 token 检查逆转录酶序列，筛出约 3500 个候选系统，再挑 20 个重点分析；其中一个 Agent 在噬菌体逆转录酶附近识别出规律性 DNA 重复阵列及伴随蛋白。人类研究者随后在实验室观察到该阵列会表达不同的短 RNA。与只生成论文假说的案例相比，这里至少跨过了**序列挖掘 → 候选缩小 → 人工实验初验**三个环节。

但“类似 CRISPR 的重复结构”不等于已证明该系统可编程、可编辑基因，团队也明确表示尚不知道 ART 的主要功能。950 个 Agent 和巨量 token 说明这是高成本并行搜索案例，尚无与相同预算的人类研究或传统生物信息学流水线的严谨效率对照；因此不能据此断言模型独立完成科学发现的通用能力。对 AI Scientist 的可迁移价值在于把可检索的原始数据、候选筛选和湿实验验证串成可复核闭环。**建议投入：了解即可（5～20 分钟）；若研究自动化实验，再读技术预印本的方法与筛选误报。**

## Part 2/3

# 系统与编译器进展

### OpenShell 0.1.0：把 Agent 权限放到工作负载之外执行

**质量：B｜重要性：高。** NVIDIA 9 月 28 日发布 [OpenShell 0.1.0 技术说明](https://developer.nvidia.com/blog/add-runtime-controls-to-ai-agents-with-nvidia-openshell)及[开源实现](https://github.com/NVIDIA/OpenShell)。其 Gateway 管理沙箱生命周期与策略，沙箱用内核控制文件和进程访问，位于 Agent 进程外的 Supervisor 检查唯一外连路径。针对配置过的 REST、GraphQL 和 MCP 流量，策略可细到同一 API 允许读取、拒绝写入；真实服务凭据留在沙箱外，在通过端点与策略检查后才替换占位凭据。策略以 YAML 定义并编译为 OPA/Rego，可在运行中更新网络规则；文件系统和进程限制变更仍需重新建沙箱。

这比要求 Agent 自觉遵守提示词更适合长周期代码执行：启动子进程、运行生成代码或委派任务后，边界仍由外部组件执行。官方给出了无网络、GitHub 只读与拒绝 POST 的可运行示例，并提供形式化 policy prover 检查**模型化的权限**是否越界。但 0.1.0 仍是早期版本；公开材料不足以证明所有协议、加密流量、跨 Agent 权限组合都已覆盖，NVIDIA 自述的对抗实验也不等于独立安全审计。[另一篇平台文章](https://developer.nvidia.com/blog/nvidia-open-agent-safety-platform-a-reference-for-continuous-in-silicon-agent-monitoring/)描述的 BlueField-4/Sentry 硬件监控是参考架构的额外层，不能当成 OpenShell 软件部署自带的能力。**建议投入：立即学习（1～3 小时），按官方只读策略示例实测允许/拒绝路径，并检查协议覆盖与容器网络前提。**

### DSX MaxLPS：固定供电预算下扩容，尾延迟需单独验收（9 月 27 日补报）

**质量：A｜重要性：中。** [NVIDIA 与 Nscale 的技术评估](https://developer.nvidia.com/blog/how-nvidia-dsx-maxlps-maximizes-ai-factory-throughput-and-efficiency/)针对静态按节点峰值预留导致的闲置功率，用拓扑分组、功率遥测、策略与动态 GPU 功率限额，在组级预算内重新分配余量。测试固定 264.4 kW 已批准供电预算、GB300 NVL72 和 Kimi K2.5 FP4 推理负载，比较 140 与 192 张 GPU：聚合吞吐由 108.45 万升至 161.84 万 token/s（+49.2%），实测总功率由 166.2 升至 198.9 kW（+19.7%）。每实例吞吐基本持平，中位和 P75 延迟在基线 5% 内，但 P99 首 token 延迟增加 17%。

这是**供电预算内增加运行实例的容量实验**，不是单 GPU 推理加速；“每预留瓦吞吐”提高的 49.2% 与聚合吞吐同幅，是因为分母始终固定为 264.4 kW。结论依赖高吞吐与低延迟实例的混合、功率曲线错峰和可靠遥测，不能直接套到所有 GPU 同时满载或尾延迟严格的集群。它提供了容量规划时应同时比较预留功率、实际功率、服务吞吐与 P99 的方法。**建议投入：了解即可（5～20 分钟）；负责集群调度或电力预算时深入复跑代表性负载。**

# GitHub 高价值项目洞察

### [radixark/miles v0.1.1](https://github.com/radixark/miles/releases/tag/v0.1.1)：把复杂模型后训练接入与训练一致性放在同一条链上

**质量：A｜重要性：高｜Evidence Maturity：M1。** 此前漏报，版本于 9 月 26 日发布。相对已介绍的 v0.1.0，增量不仅是支持更多模型：Qwen3.8-Flash-Next 与 GLM-5.3-Flash 的共置 RL 路径给出权重更新相等检查和 rollout/trainer 对数概率差记录；Kimi-K3 从专用镜像进入主线，并给出 236 步训练轨迹。多租户 Tinker 兼容网关使多个 LoRA 槽共享基座模型，而各自保存优化器状态与 checkpoint；Anthropic Messages API 接入让现有编码 harness 能通过 TITO session server 进入训练流水线。系统侧还加入 Adam/Muon 优化器状态 NVMe streaming、低精度 QAT kernel 和异步 checkpoint 路径。

最有学习价值的是**训练端和 rollout 端数值一致性如何成为接入门槛**。例如 Qwen3.8-Flash-Next 的官方 5 步实验报告 `train_rollout_logprob_abs_diff` 在 0.0083～0.0131；GLM-5.3-Flash 的 3 步实验为 0.0085～0.0098。这些是运行中的偏差读数，不是模型质量排名，也不能证明长训练稳定性。作者给出的硬件配置和任务轨迹足以沿 PR、recipe 和测试追踪实现，但跨集群吞吐、容错及大规模成本仍缺独立复现。**建议投入：深入学习（半天～2 天）。先读两个模型接入 PR 的权重映射和一致性检查，再在可负担的小模型 recipe 中跟踪 rollout → 权重同步 → trainer；不必为学习机制复制 8×4 GB300 实验。**

### [ai-dynamo/aiperf v0.13.0](https://github.com/ai-dynamo/aiperf/releases/tag/v0.13.0)：让推理压测更接近可解释的线上负载

**质量：A｜重要性：高｜Evidence Maturity：M1。** 此前漏报，版本于 9 月 24 日发布。已介绍的 AIPerf 基础架构解决了客户端先成为瓶颈的问题；0.13.0 则补足**测量有效性**：新增推测解码接受率的每请求指标、`reset_kv_cache` 和 `server_profiler` 控制钩子、按 chunk 记录 usage 以修正首个流式 chunk 合并导致的 TPS/user 虚高，并提高到达率循环定时精度。原生 Kubernetes 执行仍标为 beta；结构化工作负载加入 cache-bust，提供 vLLM bench 合成 token 采样负载的复现路径。

这些变化使“吞吐提升”可以拆成负载发生、缓存状态、推测解码接受率与服务器实际工作，而非只看客户端打印的 TPS。版本说明对应具体 PR、代码与测试，工程实体充分；但还没有跨引擎、跨机器的独立压测误差上界。**建议投入：深入学习（半天～2 天）。在固定模型和服务端版本下，对比旧版与 0.13.0 的流式 TPS、TTFT/P99、接受率及服务端遥测；再用真实 trace 验证 SLA/goodput，避免把缓存或首 chunk 口径变化误判为服务端加速。**
