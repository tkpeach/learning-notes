# 系统与编译器进展

### Helion × CompileIQ：把 kernel 配置和 ptxas 控制一起调优

**质量：A｜重要性：中｜Personal Utility：极高｜发布：2026-10-19。** [PyTorch 技术文章](https://pytorch.org/blog/one-search-two-layers-compiler-controls-inside-pytorch-helion-using-nvidia-compileiq/)把优化空间分成两层：Helion 搜索 tile、warp、流水级数等配置；CompileIQ 搜索 ptxas 的编译控制，输出 ACF 文件。两层通过寄存器压力、occupancy 和 spill 耦合，先固定一层再搜索另一层，可能错过更好的组合。接口既允许固定 `advanced_controls_file`，也允许用 `autotune_search_acf` 把多个 ACF 加入搜索，默认编译路径仍参加比较。

**基线与实测。** 作者用已经带 AOT 调优配置的 NVFP4 decode GEMV，而非朴素实现作基线；在 GB200、CUDA 13.3、Triton 3.8.0 的指定形状上，运行时间目标获得约 **4.8%** 改善，多目标搜索约 **6.9%**。它们是作者另行重测、经参考输出校验的 kernel 时间，既不是第三方复现，也不是整模型吞吐；用 occupancy 作代理目标的收益更小，不能把代理指标上升当成最终目标改善。

[Helion 代码目录](https://github.com/pytorch/helion/tree/main/pretuned_kernels)提供 kernel、形状扫描、参考基线及各架构的 AOT 文件；[CompileIQ 的 Booster Pack 文档](https://nvidia.github.io/CompileIQ/v1.0/booster_packs.html)要求先建立无 ACF 基线、检查环境并逐候选验证。ACF 与硬件、编译器环境绑定，不匹配可能产生错误结果或崩溃；联合搜索也会增加编译和测量次数，适合离线调优后固定产物。Helion 开源，CompileIQ 使用专有 NVIDIA 软件许可，不能统称为全部开源。

**投入建议：深入学习（半天）。** 从一个现成 GEMV 或 RMSNorm 例子开始，固定形状、工具链和时钟，分别比较默认、只调 kernel、加入 ACF 的结果，记录正确性、运行方差和搜索成本。学完能区分算法配置与后端代码生成的贡献，并把调优结果作为版本化构建产物管理。没有合适 GPU 时，先读配置接口和验证流程；不必为了复现百分之几的收益购置硬件。

### MLIR 静态内存规划器：arena 复用的难点在释放与别名

**质量：A｜重要性：中｜Personal Utility：极高｜技术复盘发布：2026-10-19；相关代码此前已合入。** [LLVM 复盘](https://blog.llvm.org/posts/2026-08-24-gsoc-2026-static-memory-planner/)与[基础 PR](https://github.com/llvm/llvm-project/pull/205125)展示从独立 `memref.alloc/dealloc` 到单个字节 arena 加 `memref.view` 的变换。规划器接收大小、对齐和生命周期区间；顺序排列先建立基线，best-fit 再复用生命周期不重叠的空间。arena 可在函数内分配，也可作为参数传入，方便外部 runtime 管理内存。

最有学习价值的是[后续 `scf.if` 修正](https://github.com/llvm/llvm-project/pull/213634)：直接找 alloc 的 dealloc 用户无法覆盖结果别名，手写 DFS 又难以覆盖多种控制流。实现改用 `BufferViewFlowAnalysis`，正向寻找潜在释放、反向确认一次释放可能关联哪些分配；嵌套释放的生命周期保守延伸到外层操作结束。若同一 dealloc 还可能释放未被 arena 管理的嵌套分配，就跳过该分配，不能为了扩大覆盖率删掉释放操作。

这已经有合并代码与边界测试，适合作为正确性设计案例；当前仍有 entry-block、静态形状和控制流限制，也没有可据以宣称通用模型显存或吞吐改善的系统基准。**投入建议：深入学习（半天）。** 先读 `StaticMemoryPlannerAnalysis.cpp`，再对照 PR 中结果别名、嵌套 dealloc、共享释放的测试，手算每个候选的生存区间和拒绝原因。学完可更准确地判断 bufferization、arena 与自定义加速器内存管理之间的接口，以及何时必须保守保留原路径。

### Scion：把始终在线的 Agent 工作负载放进源码管理协议

**质量：A｜重要性：中｜Personal Utility：高｜此前漏报，正文发布：2026-10-13，补充更新：2026-10-15。** [Anthropic 工程正文](https://www.anthropic.com/engineering/redesigning-source-control)报告，单仓每日合并从约 2,500 增至 30,000 以上后，团队把提交、历史查询和合并放到服务端，客户端按需读取不可变对象。changeset 只记录相对首父提交的文件变化；派生索引服务历史查询，节点与区域缓存复用对象，CI 可以通过 API 完成部分工作而免于 checkout。

团队称相对原有 Git 镜像体系，CPU/内存基础设施规模缩小约 200 倍、checkout 从分钟级降至秒级。这是特定内部工作负载的自报结果，缺少公开实现与外部同配置复测；始终在线的前提也带来可用性与故障域约束。**立即学习（1～3 小时）**：重点读 changeset、派生数据与分层缓存，给自己的 CI 画出“哪些步骤实际需要文件、哪些只需元数据”的调用图。可迁移的价值是减少无用数据物化，无需据此更换现有版本控制系统。

### TorchNeuron：Trainium 走向原生 PyTorch 设备，Beta 仍待正式开放

**质量：B｜重要性：高｜Personal Utility：高｜公告：2026-10-19。** [PyTorch 公告](https://pytorch.org/blog/introducing-torchneuron-native-pytorch-backend-for-aws-trainium/)介绍通过 PrivateUse1 与 `torch.accelerator` 将 Trainium2/3 接为 `neuron` 设备：eager 便于逐操作调试，`torch.compile` 路径经 FX、AOTAutograd、Torch-MLIR、StableHLO 生成 NEFF。它让模型代码与分布式 API 的接入边界更接近标准 PyTorch，实验性 adaptive eager 则试图减少逐操作编译和启动开销。

公告计划于 **10 月 20 日**开放 Apache-2.0 public Beta；当前不能把计划发布时间换算成已经可构建。非默认 stream 会复用硬件队列，不能推断多个 stream 对应多个并行引擎；FP8/TorchAO 仍处 private Beta。**了解即可（20 分钟）**：先对照此前 Spyre 案例阅读设备、stream 和编译链路；待代码与依赖正式公开，再验证一个小模型的 eager/compile 结果和性能。

### SGLang 0.5.22：先看 KV 准入与混合状态恢复，再看吞吐倍数

**质量：A｜重要性：高｜Personal Utility：高｜发布：2026-10-19。** [正式 release](https://github.com/sgl-project/sglang/releases/tag/v0.5.22)在 0.5.21 基础上增加模型、后端与并行组合支持，也提供 Python 3.11+ 的版本要求、安装路径和多平台镜像。这里最值得读的是分离式服务的资源生命周期，以及推测解码与持久状态之间的正确性契约。

[PR #40703](https://github.com/sgl-project/sglang/pull/40703)新增可选 `prefill_complete` 分配策略：原路径会在 prefill 未结束时预留 decode 目的 KV；新路径等最终 prefill 结果就绪才准入，避免未完成的长提示占住容量。**`early` 仍为默认**，新策略主要针对 decode KV 紧张且提示长短混合的负载，并没有让分配器或 decode kernel 本身更快。PR 明列 Mooncake、并行与缓存组合限制，以及通信双方升级要求，不能把它当作任意 PD 部署都能直接打开的开关。

作者在特定 GLM-5.2-NVFP4、KV 压力配置下报告吞吐提高 **26.8%**、p95 TTFT 降低 **48.9%**。有 CPU/GPU 生命周期测试和功能对照，但 PR 也说明部分性能、GPU 验证早于后续 rebase，最新依赖锁定与回归验证仍有缺口；这支持针对性复跑，不支持普遍性能承诺。

另一项[状态边界修复 #43029](https://github.com/sgl-project/sglang/pull/43029)已在本版交付：release 指出混合线性模型组合推测解码与结构化输出时，可能从错误的 Mamba 状态恢复；修正使用已提交长度判断追踪边界。它提醒我们，接受前缀、缓存检查点和调度器长度必须一致，kernel 数值测试不能覆盖整个请求生命周期。

**投入建议：深入学习（半天～1 天）。** 先读两项 PR 的状态与取消/恢复路径，再以 0.5.21 为基线固定模型、量化、提示分布和 KV 容量，比较 0.5.22 默认策略及受支持的新策略。分别测输出一致性、取消后资源释放、重试恢复、TTFT/TPOT 与吞吐。现有服务若使用上述混合模型组合，应优先核对状态恢复修复。
