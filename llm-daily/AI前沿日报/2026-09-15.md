# 系统与编译器进展

### Clang API Notes 获得 C++ 重载级选择能力，且保留原有按名称匹配语义

**重要性：中高。** LLVM 官方博客发布 [Extending Clang API Notes for C++](https://blog.llvm.org/posts/2026-08-21-gsoc-clang-api-notes-overloads/)，为 `Functions` 和 `Methods` 增加可选的 `Where.Parameters`，使同名 C++ 函数或方法的不同重载能够接收不同 Swift 暴露名称、可用性等外部注解；`Where.Object` 还能区分成员函数隐式对象的 `const`、`volatile` 与左值/右值引用限定。

实现并非字符串匹配补丁，而是贯穿 YAML 模型、二进制序列化、声明查找、Sema 应用和诊断。类型选择器先匹配源码书写或带语法糖的类型，再按规则回退到去糖表示，并规范化空白、别名、顶层限定符和选择器中的 nullability。缺省 `Where.Parameters` 继续作用于整个同名集合，显式空数组才表示零参数，从而维持旧 API Notes 的行为链路。当前模板函数匹配仍停留在设计阶段。对做 C++/Swift 互操作、SDK 注解或 Clang 前端扩展的人，这是一个很好的兼容性设计案例。**建议投入：了解即可（30～60 分钟）。**

# GitHub 高价值项目洞察

### Colibrì：把 MoE 专家权重当作跨 VRAM、RAM 与 NVMe 调度的数据

[JustVugg/colibri](https://github.com/JustVugg/colibri) 是 Apache-2.0 的纯 C 推理引擎，当前约 31.4k stars。它不要求整模型常驻快速内存，而让 dense 部分常驻、按路由结果从磁盘加载专家，并用分层 LRU、热点固定、一层前瞻预取、批次专家并集、异步 I/O、双 SSD 条带化和可选 CUDA/Metal/Vulkan 后端减少搬运成本。仓库已覆盖 GLM、Kimi、DeepSeek、Qwen 等九类 MoE/混合架构，并公开端到端 benchmark、质量检查与负面结果记录规范。

真正值得关注的是它把“模型能否运行”与“运行是否够快”分开：默认不静默改变模型精度或路由语义，快速存储不足只降低速度；同时明确承认历史路由会过拟合、预取在部分主机上会倒退、推测解码存在命中率盈亏平衡点。仓库给出的 GLM-5.2 数据从 25 GB 开发机冷态 0.05～0.1 tok/s，到 6×RTX 5090 全驻留 5.8～6.8 tok/s，说明它更像可复现实验平台，而非即装即用的高吞吐服务。**建议投入：立即学习（1～3 小时）。** 先读多级权重放置、I/O 流水与 benchmark protocol，再决定是否在自己的硬件上复跑。

### OpenCodeReview：用确定性流水线约束 Agent 的代码审查覆盖面与定位

[alibaba/open-code-review](https://github.com/alibaba/open-code-review) 以 Apache-2.0 开源，当前约 24.5k stars。项目源自阿里巴巴内部代码审查系统，核心不是再包一层提示词，而是让确定性逻辑负责文件选择、相关文件分组、规则匹配、评论定位和反思校验，让 Agent 专注跨文件语义推理；不同文件组可隔离上下文并并发审查。它支持 diff 与整文件扫描、OpenAI/Anthropic 兼容端点，以及 GitHub Actions、GitLab CI、Gerrit 等集成。

官方用 50 个开源仓库、200 个真实 PR、10 种语言和 1,505 个专家标注问题构建 AACR-Bench，并声称在相同底模下以约九分之一 token 获得更高 Precision/F1，但主动以较低 Recall 换取更少噪声。这些数字仍主要来自项目方，尚需独立复跑；不过“硬约束保证覆盖与定位，模型负责判断”的分工对生产级 Agent 很有参考价值。**建议投入：立即学习（1～3 小时）。** 优先审查 benchmark 数据、定位/反思模块和 CI 权限边界，再做小规模真实 PR 对照。

## Part 3/3

# 科研进展

### SQD：次二次注意力需要不同于 dense attention 的解耦服务边界

[Rethinking Heterogeneous System Disaggregation for Subquadratic Attention](https://arxiv.org/abs/2609.13134) 提出 SQD，不再按传统 attention/FFN 运算符拆分 decode，而是按二次与次二次注意力的算术强度和状态占用拆分。对稀疏注意力，它把需要遍历完整 KV 的 top-k 选择与静态内存占用的 top-k attention+FFN 分开；对线性和滑窗注意力，则把 dense attention 层与次二次 attention+FFN 层分开映射到异构资源。

作者在调整后的 8×B200 异构系统代理上报告 GLM-5.2、Nemotron 3 Ultra、Gemma 4 31B 相对最强纯 GPU 基线的 token/J 分别提升 53%、31%、56%；Rubin+LPX 的解析模型给出 1.2～1.5 倍更紧延迟和最高 3.6 倍吞吐。局限也很明确：核心结果依赖系统代理与解析模型，尚非跨真实集群的生产复现。它的价值在于提醒 serving 架构不要把新注意力机制硬塞进 dense-era 的解耦模板。**建议投入：深入学习（半天以上）。**

### AMDKernelVault：把 AMD kernel Agent 从零散样例推进到大规模可执行训练资产

[AMDKernelVault](https://arxiv.org/abs/2609.12471) 发布面向 AMD CDNA GPU 的 HIP/Triton kernel 语料与训练框架。HIPKernelGen 和 TritonKernelGen 从 PyTorch 参考实现出发，自动生成候选、在 ROCm 下编译验证并在 AMD 硬件上测延迟；资产包括 62,153 个执行验证的 HIP kernel、2,377 个生产背景 ROCm Libraries 问答条目和 39,893 个 Triton kernel。

作者以 Qwen3-8B 做监督微调和执行感知强化学习，在固定预算下报告 PyTorch-to-HIP 34.0% Pass@1、TritonBench-G 33.2% Corr@3、ROCmBench 41.94% Corr@3，正确率在对照模型中最高，但编译率和速度并未全面领先。论文同时开放数据与生成/训练代码，因而具有直接复跑价值；不过当前结果仍是作者自评，硬件覆盖和真实性能泛化需要外部验证。**建议投入：深入学习（半天以上）。**

### Repository SKILL 优化的提升可能小于 Agent 的运行方差

[Skill Issue: Lessons from Optimizing Repository SKILLs for Coding Agents](https://arxiv.org/abs/2609.12742) 用“把已合并 PR 回退到统一基线提交”构造更难的仓库任务，并以同一 Agent 有无 SKILL 文档的差值评价文档。三个 Kotlin 仓库上，GEPA 优化的文档平均提升 4.9 个百分点，SkillOpt 仅比种子文档高 0.1 个百分点；但在单仓库可提供的数据规模下，GEPA 的提升仍无法与 Agent 运行方差可靠区分。

论文的关键不是否定仓库知识，而是把“文档读起来更好”与“可测的任务收益”拆开：维护者确实在生成文档中发现了需要项目经验才能获得的知识，但小样本 benchmark 不足以证明稳定增益。对维护 `AGENTS.md`、`SKILL.md` 的团队，应该采用冻结基线、真实历史任务、同 Agent 成对 A/B 和多次重复，而不是用容易饱和的合成题做单次验收。**建议投入：立即学习（1～3 小时）。**

# 本期最值得关注

1. **SQD 的次二次注意力异构解耦。** 它把模型架构变化直接转译为资源切分原则，并给出显著能效与吞吐潜力；建议半天精读建模假设、硬件代理和各注意力变体的拆分方式，再等待真实 Rubin/LPX 或多机复现。
2. **AMDKernelVault 的可执行 AMD kernel 训练资产。** 大规模执行验证数据、自动生成流水线与训练代码同时开放，能补足 CUDA 中心化的 kernel Agent 生态；建议先复跑小规模 HIP/Triton 子集，并把正确率、编译率与加速比拆开评估。
