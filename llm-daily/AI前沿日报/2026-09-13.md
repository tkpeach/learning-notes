## Part 2/3

# 系统与编译器进展

### 此前漏报：vLLM 把 KV cache 外卸扩成可组合的分层缓存

**重要性：高。** vLLM 于 9 月 10 日发布的 [Tiered KV Cache Offloading](https://vllm.ai/blog/2026-09-10-tiered-kv-offloading) 将 KV cache 从 GPU 扩展到 CPU DRAM、文件系统、S3 兼容对象存储和节点间传输。核心不是简单增加一个 swap 层，而是把张量并行分片整理为与执行后端无关的 canonical layout，使缓存可以跨 worker、跨后端复用；GPU 恢复采用异步、非阻塞路径，并在真正需要时才分配加速器空间。

该能力自 vLLM v0.22 起可用，节点间复用通过 ZeroMQ 协调元数据、NIXL/RDMA 传输数据，集群级路由和所有权仍交给 llm-d 等外部编排层。它同时覆盖混合注意力和 Mamba 状态，并提供 Prometheus 指标，但官方文章没有给出可跨工作负载泛化的统一性能结论。学完后能把 prefix reuse 从“单机显存命中”扩展为缓存层级、数据布局、传输和调度共同决定的问题，并能为自己的服务设计容量、带宽和恢复延迟指标。**建议投入：立即学习（1～3 小时）。** 先读 canonical layout、异步恢复和 P2P 协议，再用自己的前缀复用率与 SLO 做小规模压测。

### 此前漏报：vLLM 拆解 MiniMax M3 在 MI355X 上的 3.14 倍吞吐提升

**重要性：高。** [Following the Bottleneck](https://vllm.ai/blog/2026-09-10-minimax-m3-mi355x) 记录了 MiniMax M3 在 8×AMD MI355X 上的连续优化。在固定 MXFP8 拓扑、并发 32 的作者配置中，每 GPU 输出吞吐从 109.1 提升到 342.4 token/s，TTFT 从 1.46 秒降到 0.67 秒，TPOT 从 69.1 毫秒降到 22.1 毫秒；并发 128 时吞吐从 297.8 提升到 623.7 token/s。共享专家融合在低并发端贡献尤其明显，而单个 index kernel 最高 48.9% 的提升最终只转化为约 3.3% 的端到端收益，说明局部 benchmark 不能代替系统剖析。

文章还报告 MXFP4 在改变 TP4→TP2 后达到 943.5 token/s/GPU，但这不是固定拓扑下的纯 kernel 加速，不能和前述 3.14 倍直接混为一谈。学完后能理解 MoE serving 中共享专家、稀疏索引、通信重叠、缓存块复用和并行拓扑如何轮流成为瓶颈，并能更谨慎地审计“倍数提升”的基线。**建议投入：立即学习（1～3 小时）。** 按 PR 顺序复原每步收益，优先区分固定拓扑优化与拓扑变更。

### 此前漏报：Helion × HF Kernels 把自动调优结果直接带到模型分发层

**重要性：中。** PyTorch 于 9 月 11 日发布的 [Helion × HF Kernels](https://pytorch.org/blog/helion-x-%F0%9F%A4%97-hf-kernels-building-and-shipping-out-of-the-box-performant-kernels/) 将 Helion 接入 Hugging Face Kernels。Helion 以接近 PyTorch 的 tile DSL 描述计算，并自动搜索 lowering 策略；HF Kernels 则负责打包、发现和加载。作者进一步把离线调优结果压成按输入形状与硬件选择配置的决策树，让使用者无需在部署时重新承担调优成本。

在作者的 H100 attention 测试中，19 个调优形状相对 PyTorch SDPA 的几何平均加速为 1.20 倍，10 个 held-out 形状中 9 个获益、几何平均 1.17 倍；B200 linear-attention 端到端结果约为 1.31～1.33 倍。数据仍局限于少数 kernel 和硬件，尚不能外推到任意模型。学完后能理解高层 kernel DSL 的性能价值怎样通过搜索、配置选择和制品分发落地，也能判断何时应预调优、何时保留运行时搜索。**建议投入：了解即可（5～20 分钟）。** 重点看决策树分发和 held-out 形状结果；有自定义 kernel 需求时再复现。

## Part 3/3

# 科研进展

### 重复数据下，MoE 可能比 Dense 模型更早过拟合

[Data Scarcity and Model Sparsity: Mixtures-of-Experts Overfit More to Repeated Data](https://arxiv.org/abs/2609.11917) 比较了约 8000 万至 10 亿 active parameters、最高 85 亿 total parameters 的 dense 与 MoE 模型。作者发现，数据重复较少时 MoE 仍有参数效率优势，但重复约 4 次就开始明显受损，而相当规模的 dense 模型可容忍超过 8 次；重复 32 次后，MoE 的优势基本消失。更强的 masking 正则可让 MoE 在超过 64 次重复时重新优于 dense，但仍追不上使用独特数据训练的结果。

**质量：B；证据成熟度：M0。** 多规模对照和 routing 分析支持“专家早期固化、重复放大记忆”的解释，但目前只有作者论文，尚未确认代码、训练 recipe 或独立复现。学完后能在数据受限训练中把稀疏度、重复率和正则化联合纳入 scaling 决策，而不是默认 MoE 总能用总参数量换效率；也能为重复数据实验增加路由稳定性和专家专门化指标。**建议投入：立即学习（1～3 小时）。** 先核对参数匹配、重复率定义和 masking 消融，再决定是否在自己的预训练配方中复现。

### AgentZip：利用高扇出沙箱之间的结构性冗余压缩内存

[Memory Compression for High-Fanout Agent Sandboxes](https://arxiv.org/abs/2609.11294) 面向一个 Agent 同时启动大量隔离沙箱的场景，利用模板页与实例页、多个沙箱之间的重复内容做压缩，并通过更宽松的候选页选择和恢复时预取降低解压开销。关键调度思想是把压缩放到 Agent 等待 LLM 响应的空档，而不是和工具执行争抢关键路径。

**质量：B；证据成熟度：M0。** 作者报告沙箱内存容量最高提升 8.7 倍，而 Linux 基线为 2.1 倍；激进压缩带来的 slowdown 从 3.1 倍降至 1.40 倍。结果直接对应高扇出 Agent 基础设施，但目前未确认公开实现，工作负载、页共享边界和尾延迟仍需外部验证。学完后能把 Agent sandbox 的成本拆成模板冗余、实例工作集、LLM 等待空隙和恢复延迟，并能判断压缩、写时复制与快照复用各自适用的位置。**建议投入：了解即可（5～20 分钟）。** 先看内存来源分解和 prefetch 策略；等代码或第三方结果出现后再投入复现。

# 本期最值得关注

1. **vLLM 分层 KV cache。** 它把 KV 复用从单节点显存优化提升为数据布局、异步恢复、远端传输和编排协同的问题。建议投入 1～3 小时读完设计与实现边界，并用自己的命中率、对象大小和 SLO 估算 GPU→DRAM→远端层级是否真正划算。
2. **MoE 的重复数据过拟合。** 这条结果会直接改变数据稀缺场景下对稀疏模型的默认判断。建议投入 1～3 小时核对规模匹配、重复率和正则化消融，再把路由稳定性与专家专门化加入训练监控。
