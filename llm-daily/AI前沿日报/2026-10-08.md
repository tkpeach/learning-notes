# 业界进展

### GPT‑6 进入 ChatGPT：Intelligent UI 与边思考边回答

**质量：B｜重要性：高｜原始发布：2026-10-07。** [OpenAI 发布说明](https://openai.com/index/gpt-6-for-everyone/)明确，这次是 ChatGPT 对话体验更新：Plus、Pro、Business 和 Enterprise 使用面向日常对话调优的 GPT‑6 Sol，Free 和 Go 使用 GPT‑6 Luna；付费层自 10 月 7 日推出，免费层自次日扩展。发布方特别说明，Work 与 Codex 所用模型不因本次更新而改变。它也不是将此前的 GPT‑6 名称重新首次发布，而是将这一代模型及新交互能力扩到 ChatGPT。

**技术增量。** Intelligent UI 让模型在文本之外选择图表、表单、按钮等交互组件。官方描述了原生、可流式生成的组件库与边生成边处理界面的编译器，界面因此可以逐步出现，而不必等完整回答结束；训练和评测也纳入内容组织、布局、清晰度及是否需要交互的判断。另一条路径是把推理与回答交错进行，先给有用的部分结果，再继续补充。官方内部评测称，GPT‑6 Extra High 在与 GPT‑5.6 Medium 近似的起答时间下取得高于 GPT‑5.6 Extra High 的任务总分；需联网问题的 GPT‑6 Instant 平均早 44% 开始作答。这些数字衡量起答时间和指定内部任务表现，尚不能证明复杂任务的完整完成时间、事实质量与 UI 可用性都同步改善。

**学习与使用边界。** 对知识学习和轻量工具，真正值得验证的是交互组件能否减少反复追问、是否保留来源与可复制结果，以及渐进回答会否过早给出误导性结论。对开发者，官方说明针对 ChatGPT 产品体验，不能直接推断同一组件协议、编译器或行为已经开放到 API / Codex。[对应系统卡](https://deploymentsafety.openai.com/gpt-6-october)提供部署安全评测，但性能比较仍主要是发布方内部结果；建议用自身的检索、长任务和可访问性场景测试。

### Claude Haiku 5.5：高频任务的能力与成本组合改变

**质量：B｜重要性：高｜原始发布：2026-10-07。** [Anthropic 发布说明](https://www.anthropic.com/claude-haiku-5-5)显示，Haiku 5.5 是面向大量短任务的小模型，首次为 Haiku 系列提供可调 effort，模型标识为 `claude-haiku-5-5`，已通过 Anthropic 平台及主要云平台提供。定价分 10 万 token 提示词阈值：较短提示词每百万输入 / 输出 token 为 0.10 / 0.50 美元，超过阈值则为 0.50 / 2.50 美元；其“平均运行成本下降约 75%”是发布方按任务用量估计，不等于所有请求的固定账单降幅。Sonnet 5.5 的缓存读取价格也同期减半，比较路由成本时应把缓存命中率计入。

**能力证据与可比性。** 官方在 OSWorld 2.1 的离线子集报告 Haiku 5.5 成功率 72.4%，Haiku 4.5 为 15.7%，Sonnet 5.5 为 83.9%；无工具 Humanity’s Last Exam 为 45.9% 对 10.2%；Terminal‑Bench 4.0 为 39.2% 对 0.0%。差距很大，但这些是发布方统一展示的特定评测设定，OSWorld 明确是离线子集，不能当作完整线上桌面任务成功率。发布页也引用 AlphaSense 的 400 个文档问答从 0.76 到 0.84、HubSpot 三次运行平均 92.8% 等早期客户评测；它们补充了真实用途信号，尚不是可独立复跑的公开基准。

**适用边界。** 适合先在检索后抽取、摘要、压缩和窄范围子任务上做质量—延迟—总成本对照，再决定是否替代大模型。涉及长轨迹编码、复杂规划和多工具恢复时，官方自身仍将 Sonnet / Opus 定位为更强选择；分层路由比单纯用最低单价更稳妥。对用户自己的工作流，应分别测低 effort 与高 effort、10 万 token 阈值两侧、缓存读取比例和失败重试成本。

# 系统与编译器进展

### vLLM 三周内将 DeepSeek‑V4.1‑Flash 的 Agent 吞吐推高 5.3 倍

**质量：A｜重要性：高｜原始发布：2026-10-07。** [vLLM / Inferact 技术报告](https://vllm.ai/blog/2026-10-07-deepseek-v41-flash)记录相对该模型首日 vLLM 版本的完整优化过程：在低并发场景加速 1.9 倍，在 150 token/s 约束下的指定 Agent 负载吞吐提高 5.3 倍。基线是同一 serving 体系的早期实现，而不是其他引擎或同规格模型。该模型的因果编码器—解码器结构、共享压缩的全局 KV、短滑动窗口 KV 与专用内核，使性能瓶颈不同于普通 dense Transformer。

**关键机制。** 前缀缓存命中后，逐层精确重建滑动窗口 KV 会扩大重放范围；vLLM 改为只重放末尾 128 token 的有界方案，并在部分 decoder 层省掉大部分 prompt prefill。这个计算有意牺牲逐位一致性，官方给出约 30% 的首 token 时间下降，另配 CUDA graphs 避免短执行路径的启动开销。内核侧接入 DeepSeek 的 MegaAttention、Mega‑mHC、Mega‑Gate 与 DeepSelect，融合通信与前后算子，利用并行侧流隐藏部分 mHC 成本；FP4 KV 与共享布局共同降低长上下文显存占用。这些增益来自模型结构和运行时协同，不能归于某一个 kernel。

**核验与落地。** 性能结果针对 SemiAnalysis AgentX 负载及指定 GB200 / GB300 配置，低时延和高吞吐采用不同并行策略。官方对部分准确率基准做了有界重放检查，但小幅差异仍受抽样误差限制；需要在长轨迹、工具调用和不同前缀命中率上验证非逐位一致策略的任务质量。工程上最可迁移的做法是按前缀命中、prefill、decode、KV 字节数和通信分别测量，并把 throughput 约束、并发与硬件版本写清楚；5.3 倍不宜外推到任意生产流量。

### Codex 0.161.0：权限与恢复链路的工程修正

**质量：A｜重要性：中｜原始发布：2026-10-07。** [官方 release 记录](https://github.com/openai/codex/releases)列出 0.161.0 稳定版的模型目录、MCP 登录和后台任务改动，同时修复权限升级时对已拒绝文件读取或网络访问的处理、同轮后台任务权限继承、线程恢复与重试等问题。这些变动的共同点是减少长任务中“看似继续、实际授权或上下文已偏离”的状态错误；如果本地 CLI 工作流依赖 MCP、后台执行或会话恢复，应核对升级后这几条链路。发布记录中的默认模型目录调整不意味着本聊天的日报自动改用其他模型；当前窗口继续沿用用户选择。
