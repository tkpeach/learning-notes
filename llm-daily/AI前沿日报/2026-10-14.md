# 业界进展

### Gemini 4 Argon：正式开放后，如何判断能力、成本和工程边界

**质量：A｜重要性：高｜Personal Utility：高｜正式开放：2026-10-13。** [Google 本次公告](https://blog.google/innovation-and-ai/models-and-research/gemini-models/introducing-gemini-4-argon/)是 [9 月 30 日初次发布](https://blog.google/innovation-and-ai/models-and-research/gemini-models/gemini-4-argon/)后的可用性变化：开发者和企业现在可经付费 API 全球调用，Ultra 用户可在 Antigravity 使用，Gemini 应用与搜索 AI Mode 面向 Ultra/Pro 用户开放。不能把今天误写为模型首次发布，也不能把应用订阅等同于免费 API 配额。官方[定价页](https://ai.google.dev/gemini-api/docs/pricing)明确 Argon 无免费 API 层；标准档至 11 月 30 日每百万输入/输出 token 为 **2/10 美元**，12 月 1 日起为 **4/20 美元**。输出价包含思考 token；隐式缓存输入为标准输入价的 5%，暂不支持显式缓存。批处理价格减半，但延迟和任务形态需另行评估。

**能力证据。** Google 在初次发布时报告 DeepSWE v1.1 **77.9%**、AutomationBench **51.3%**、LVBench **91.7%**，本次强调 Vals Index 排名和跨领域工作流。更值得核对的是可追溯的工程产物：官方称 Argon 协助 ADK 的长会话内存准备和冷导入分别优化 **40%**、**21%**，并链接了[代码变更与工程复盘](https://developers.googleblog.com/optimizing-a-200000-line-python-codebase-overnight-with-gemini-4-argon/)；Chromium、xTB、Gemma 推理优化也提供上游变更入口。这些支持“能参与复杂代码工作流”，但速度增益属于具体代码、硬件和人机流程，不能归结为模型独立完成或泛化到任意仓库。Google 报告 Antigravity 内部 agent 代码提交增加逾 35%、回滚减少近三分之一；这是内部使用观察，缺统一公开对照。榜单、案例和模型能力评估分属不同证据层，当前公开模型卡链接仍未提供可核验的完整正文。

**长任务与工具边界。** 官方[思考与 token 文档](https://ai.google.dev/gemini-api/docs/thinking/)将输入、思考、输出放在共用的 **1,048,576 token** 窗口；普通同步请求的最大生成上限仍为 **65,536 token**，超过须用后台长生成和续接机制。因此“百万 token 输出”是特定调用路径的能力，不是默认一次同步请求可稳定吐出百万正文。`max_output_tokens` 同时截断思考和可见输出，额度设得过低可能得到空/残缺答案却仍支付思考费用；降低 thinking level 才是更可控的降时延方式。生产集成还需核查长任务的续接、失败恢复、工具签名和缓存命中率。

**投入建议：深入学习（半天～1 天）。** 先用自己的一组长代码库修复、带工具多轮任务和长文档问题，对比现有主力模型的正确率、人工返工、首 token/总耗时、思考 token 与最终账单；分别测同步和后台长生成，固定任务与预算。尤其关注 12 月涨价后是否仍有净收益。可把本次开放视为值得实际试测的能力更新，暂不依据厂商榜单直接认定全面领先。

## Part 2/3

# 系统与编译器进展

### vLLM：双向 KV 传输减少多轮 Agent 的重复预填充

**质量：A｜重要性：高｜Personal Utility：高｜此前漏报，原始发布：2026-10-12。** [vLLM 官方技术文章与复现实验](https://vllm.ai/blog/2026-10-12-bidirectional-kvxfer-multiturn-agentic-workload)针对预填充/解码分离服务的真实缺口：旧主路径仅将 KV 从 prefill 传给 decode；下一轮对话若 prefill 本地缓存不命中，历史提示与上一轮生成内容仍要重新算。新路径保留 decode 端完整会话 KV，让感知缓存的路由器传递块位置元数据，prefill 通过 NIXL 反向读取 KV 后只算新后缀；大块张量不经过路由器。这保留了原有 prefill→decode 流程，并在可复用时补上 decode→prefill。

**证据与代价。** 作者提供 vLLM v0.21.0 起的参数、示例路由器与逐步复现指南。在一台 prefill 加一台 decode 的 AWS P5en/EFA 部署中，Qwen3-32B 的 24k 提示首 token 时间由 **778 毫秒降至 460 毫秒**，GLM-5-FP8 的 20k 提示由 **2,334 毫秒降至 702 毫秒**。实验刻意关闭 prefill 的前缀缓存，模拟其缓存被逐出或路由至另一节点，因而不是“所有多轮服务都能提高 3.3 倍”的证明；还需和已有高命中率的本地前缀缓存比较。默认 `decoder_kv_blocks_ttl` 为 480 秒且不自动续期，会占用 decode 显存；少于默认 64 token 的可复用部分选择本地重算，避免网络传输得不偿失。规模化部署需验证多会话内存压力、跨节点失效、会话黏性和路由器状态恢复。

**投入建议：深入学习（半天～1 天）。** 先读文章的块位置生命周期和[复现实验](https://vllm.ai/blog/2026-10-12-bidirectional-kvxfer-multiturn-agentic-workload)，再以本机真实对话间隔、前缀命中率及网络带宽复测 TTFT、每 GPU 吞吐和被保留 KV 的显存成本。该机制的长期价值是把跨轮状态位置纳入服务调度，而不只是优化单轮 kernel。

### IBM Spyre：Inductor 扩展在非 GPU 加速器上的实测边界

**质量：A｜重要性：中｜Personal Utility：高｜发布：2026-10-13。** [PyTorch/IBM 技术正文](https://pytorch.org/blog/extending-inductor-for-the-ibm-spyre-accelerator/)承接此前“将 Spyre 注册为原生 PyTorch 设备”的工作，进一步解释 `torch.compile` 后端：Dynamo/AOTAutograd/Inductor 仍是主链路，设备专属的 decomposition、lowering 与调度前 pass 处理 **128 字节 stick 粒度数据移动、每核 2 MB scratchpad、静态核分工**，再由专有 DeepTools 编到设备指令。它不是零成本“换个 backend”或完整开源编译栈：关键调度前 pass 目前要给 `GraphLowering.codegen()` 打补丁，正式上游扩展点仍在讨论。

**实测与局限。** 作者给出单核 softmax 片上驻留优化 **32.51→23.67 微秒**，批量矩阵乘通过布局调整降低 kernel 时间 **29%～69%**，融合 MLP 中协同选择分工与 scratchpad 分配使 kernel 约快 **17%**；合成图里的片上 relayout 为 **1.1 微秒**，对比原先强制落显存的 **80 微秒**。数字分别对应不同 kernel，不能相加当端到端模型收益。新扩展代码约 3.86 万行，相比旧独立编译栈约 27.3 万行，但复用了 Inductor，不能简单解释为相同功能“纯代码减少七倍”。**建议立即学习（1～3 小时）**：沿 FX→LoopLevelIR→预调度 pass 跟踪布局、分片、scratchpad 共优化，再核对上游 hook RFC；适合作为设计非 GPU 后端时如何守住既有编译主路径的案例。

### NVIDIA Run:ai：集群 GPU 编排从产品描述变成可读源码

**质量：A｜重要性：高｜Personal Utility：中高｜发布：2026-10-13。** [NVIDIA 原始公告](https://developer.nvidia.com/blog/nvidia-runai-is-now-open-source-as-part-of-nvidia-dsx-ai-factory-platform/)与[官方 `dsx-ai-factory/run-ai` 仓库](https://github.com/dsx-ai-factory/run-ai)确认开放的并非只有调度器或 README：仓库包含控制面、集群控制器、安装器、CLI、客户端、负载测试和基于 Kind 的本地构建部署脚本，顶层标明 Apache-2.0。完整平台把项目/部门配额、工作负载生命周期与 Kubernetes GPU 调度连起来；KAI Scheduler、GPU Fractioning Operator、KAI Resource Management、Workload Map 四部分又可单独采用。尤其值得看的是 Workload Map 对 PyTorchJob、RayCluster、KServe 等不同 CRD 的统一工作负载描述，及 KAI 的 gang、fair-share、拓扑感知和 GPU 共享决策：这比单纯宣称提高利用率更有架构增量。

**判断边界与实践路径。** 公开代码与本地启动链路足以支持质量 A，但公告未给可复现的跨集群吞吐或利用率对照，不能从“生产级”措辞推断迁移收益。NGC Community 产品的下载须接受额外产品条款，社区版也不含企业支持；单独组件与整套安装的集成成本应分开。建议**深入学习（半天）**：先读[仓库架构和 `local-dev.sh`](https://github.com/dsx-ai-factory/run-ai)，把控制面、集群服务、调度器与 CRD 映射画清；若已有 Kubernetes GPU 集群，再用相同配额、拓扑和混合训练/推理负载对照原调度方案，记录排队时间、GPU 空闲、抢占与故障恢复。没有多租户调度需求时先学设计，无须部署全平台。
