# AI 前沿日报｜2026-09-30

## Part 1/3

# 今日总览

北京时间 9 月 29 日至 30 日的核心变化是 [GPT‑6.1 Sol](https://openai.com/index/introducing-gpt-6-1-sol/) 将高端模型在代码、电脑操作和专业任务上的部分能力下移到较低价格层；此前漏报的 [Claude Sonnet 5.5](https://www.anthropic.com/claude-sonnet-5-5) 则在维持 Sonnet 5 单位价格的同时，显著改善任务效率。两家公布的任务成本、评分和速度采用不同环境与口径，不宜拼接为统一排名。系统学习方面，[MaskRay 的链接器 I/O 实测](https://maskray.me/blog/linker-io-tricks-and-their-downsides)尤其值得读：它把“更快”的条件与文件语义、计量和内存代价放在同一张图中。

# 业界进展

### GPT‑6.1 Sol：高能力下移，关键是同一任务的完成成本

**质量：A｜重要性：高。** OpenAI 于 9 月 29 日发布 GPT‑6.1 Sol。相对 GPT‑6 Sol，它最有意义的变化不是单一 benchmark 冲高，而是长周期编码、专业文档、电脑操作和科研任务中**能力与任务成本同时改善**。在 DeepSWE 1.1，官方称它以较低推理强度和成本，比 Sol 的最佳成绩高 6.4 个百分点，并达到 Astra 的成绩；在 AutomationBench 1.0.6，同为 medium 设置时比 Sol 高 4.8 个百分点，比 Claude Opus 5.5 高 2.2 个百分点、任务成本约三分之一。OSWorld 2.0 离线集采用 *partial reward*：max 设置下比 Sol 高 7 个百分点，与 Astra 相差 2.1 个百分点、任务成本约七分之一。Terminal-Bench Science 0.1 则是另一个边界：Sol 6.1 的 max 成绩较 Sol 超过两倍，平均每任务 5.47 美元，但 Astra 仍取得测试模型中最高的 68.1%。这些均为 OpenAI 发布的评估；竞品分数来自公开报告，系统提示、工具和 effort 可能不同，不能当作独立、严格同条件的跨厂商胜负。

**部署成本与能力边界。** [API 模型页](https://developers.openai.com/api/docs/models/gpt-6.1-sol)列出标准价每百万输入 2 美元、缓存输入 0.10 美元、输出 10 美元；缓存输入比上一代 Sol 低 50%。但超过 272K 输入 token 时，**整次请求**输入和缓存费率变为 2 倍、输出变为 1.5 倍，长上下文服务不能直接用标价估算成本。上下文上限 105 万 token、最大输出 12.8 万 token，支持文本与图像输入、文本输出；工具调用走 Responses API，`reasoning.effort` 支持 low 至 max，**不支持 none/minimal**。官方事实性测试在刻意挑选的困难纠错提示上，low effort 含事实错误的回答占比从 11.4% 降到 7.7%；这不是日常提问错误率。发布时已向 Plus、Pro、Business、Enterprise、Edu 的 ChatGPT Work 和 Codex 开放，也可在 API 用 `gpt-6.1-sol`；Chat 尚未开放。所谓最高 8 倍的 Sol 6.1 Ultrafast 仍是“未来几天”，不能计入当前吞吐。

**安全与实际选择。** [安全补遗](https://deploymentsafety.openai.com/gpt-6-1-sol)把模型按网络安全 Critical、生物化学 High 对待，并沿用 Astra 的防护栈；这些分类说明部署措施，不能替代具体工作流验收。若你的任务是大量仓库修改、文档读取或电脑操作，先在同一代码库和工具配置下，用 Sol 6.1 与当前 Sol/Astra 比较任务成功率、人工返工、总 token、缓存命中、墙钟时间和每成功任务成本；若失败代价很高，仍需保留 Astra 的对照。**建议投入：立即学习（1～3 小时），先读发布文的任务成本曲线与 API 长上下文计价，再做小规模配对试验。**

### Claude Sonnet 5.5：同价但少走步骤，迁移有真实兼容成本（9 月 28 日补报）

**质量：A｜重要性：高。** Anthropic 于 9 月 28 日发布 Sonnet 5.5，位于 newsroom 上次已见条目之后，此处按原始日期补报。与 Sonnet 5 相比，每百万输入/输出 token 仍为 2/10 美元、缓存读取 0.20 美元；官方称多数工作因所需 token 更少，**每任务成本最高降低 30%**，输出速度提高超过 30%。这不是 API 单价打折，也不是所有工作均可节省 30%。外部试用者提供了有用但尚未独立复核的任务证据：Slack 报告输出 token 约少 14%；Balyasny 在其 2441 项金融任务上报告每答约 121K token，对照 Sonnet 5 的 497K。两者的任务分布不同，不能外推成通用节省率。

**能力增量与测试口径。** [发布报告](https://www.anthropic.com/claude-sonnet-5-5)给出 Terminal-Bench 4.0 的 70.6% 对 Sonnet 5 的 10.3%，CursorBench 4.0 的 55.5% 对 34.1%，OSWorld 2.1 的 80.1% 对 57.0%（*partial reward*）。跨模型比较需谨慎：FrontierCode 1.1 主集上 Sonnet 5.5 在 xhigh 为 52.1%，升到 max 反而降至 46.2%；Anthropic 将部分下降归因于代码审查 skill 引入额外子任务，造成超时或越界修改。这个反常结果说明 **harness、工具调用和 effort 是被测系统的一部分**，推理预算更高不保证可合并的补丁更多。Anthropic 也明确保留 Opus 5.5 在复杂、开放任务中的优势。上下文上限 100 万 token、最大输出 12.8 万 token，适合长文档和多文件任务，但仍应按实际历史长度和缓存开销核算。

**工程迁移。** API 标识为 `claude-sonnet-5-5`，Claude 应用默认 medium effort、平台 API 默认 high；模型默认启用 adaptive thinking。旧代码若传 `thinking: disabled` 会收到 400，需要改为 `between_tools`（仅适用于 low/medium/high）；强制指定工具与重排历史中的签名思考块也会破坏工具循环。[官方迁移指南](https://platform.claude.com/docs/en/models/sonnet-5-5/migration-guide)要求保留原样思考块并重新扫描 effort/成本。高风险网络安全请求可能回退到 Sonnet 5，测试结果应记录实际执行模型。**建议投入：立即学习（1～3 小时）；用固定的日常 bug 修复与文档任务比较 Sonnet 5、5.5 和 Opus 5.5 的成功率、耗时、工具回合及总价，再按迁移清单做兼容测试。**

### Agents API 新增电脑操作：托管执行链更完整

**质量：B｜重要性：高。** [OpenAI DevDay 2026 官方汇总](https://openai.com/index/devday-2026-recap/)确认 Agents API 已纳入[电脑操作工具](https://developers.openai.com/api/docs/guides/agents-api/tools/computer-use)，并把多 Agent、工具检索、工具调用和上下文压缩带入开发者可调用的托管执行环境。相对只靠模型生成工具请求，关键增量是较长任务可在有文件、代码、沙箱和会话状态的同一运行链中操作软件；应用仍需自己设计权限、审批、恢复与验收。官方已有接口文档，但尚缺跨应用的可靠性、失败恢复和总成本独立数据，故按 B 级处理。当前访问范围与套餐也有限。**建议投入：了解即可（5～20 分钟）；若要构建电脑操作 Agent，再做“失败后可恢复”和权限越界的端到端小试验。**

# 系统与编译器进展

### 链接器 I/O 技巧：快路径收益要连同 inode 与计量语义一起看（9 月 20 日补报）

**质量：A｜重要性：中｜Personal Utility：极高。** LLVM lld 维护者 MaskRay 在 [原始实测](https://maskray.me/blog/linker-io-tricks-and-their-downsides)中对比 mold、wild 与 GNU ld/gold/lld 的三种 I/O 技巧：原地覆盖旧输出、fork 后由父进程提前退出、以及 `MADV_HUGEPAGE`。这篇文章的价值在于沿**已知正常链路“新 inode → 成功后 rename”**解释每种优化改变了什么语义。原地覆盖在热 page cache 下可省一点写入成本，但硬链接指向相同 inode：作者构造失败重链接，证明另一个链接名仍指向半写入的二进制文件。旧输出不在缓存时，原地覆盖 2 GiB 文件反而先读入旧页，单机测试耗时 3.89 秒；新建 inode 为 0.38 秒。结果来自 Linux 6.18、SATA SSD 的特定环境，不能视为通用吞吐数字；它揭示的是优化对缓存状态极端敏感。

提前 fork 的父进程在子进程完成主要工作后通知构建系统并退出，可在 4 KiB 页场景省 60～70 ms，而大量 huge page 时约省 10 ms；代价是 `wait4`、`time` 和默认 gdb 跟踪的进程已非真正干活的子进程，内存释放期间构建任务槽位也可能提早腾出。作者用 cgroup 验证这一短暂但真实的峰值内存。对 huge-page 提示，ext4 上一次测试从不提示的 2.877±0.044 秒变为提示后的 3.374±0.357 秒，伴随约 550 次内存整理停顿，说明“要求大页”可能把内核整理成本压回关键路径。**适用边界**是内核、页策略、剩余连续内存和输出所在文件系统；作者没有证明所有平台都该关闭这些选项。

对 C++ 构建系统而言，学完可以更准确地设计重链接基准：同时记录 cache 冷热、输出 inode/硬链接、失败回滚、真正子进程的 CPU/RSS、cgroup 峰值和尾延迟。**建议投入：深入学习（半天～2 天）。先复做硬链接失败案例，再用 `--no-fork` 与常规模式对照 `time`/cgroup 指标；只在可控制的实验目录运行，不要用生产构建产物作试验。**

# GitHub 高价值项目洞察

### [NVIDIA/TensorRT-Model-Connect](https://github.com/NVIDIA/TensorRT-Model-Connect)：从模型接入到 C++ 运行时的纵向契约

**质量：B｜重要性：高｜Evidence Maturity：M1。** 项目并非今日新建；NVIDIA 于 9 月 29 日的[工程复盘](https://developer.nvidia.com/blog/ai-native-by-design-lessons-learned-from-building-nvidia-tensorrt-model-connect/)使其开发方法值得重新审视。仓库提供可运行的 `trtmc build Qwen/Qwen3-0.6B → .bundle → trtmc run` 路径，构建端读取 Hugging Face 权重并生成 TensorRT 工件，运行端可通过 C++ task API 使用 bundle，无需在目标进程保留 Python/PyTorch。相对逐模型拼接导出脚本、后处理和部署代码，其关键设计是让 **family 自有 builder、运行策略、描述符和测试**组成纵向切片；[扩展指南](https://github.com/NVIDIA/TensorRT-Model-Connect/blob/main/website/docs/extend/add-runtime-strategy.md)要求描述符验证、C++ 单测和具体模型 E2E 同时通过，不把“可编译”当作模型语义正确。

这套契约很适合研究 C++ 推理系统如何接纳快速变化的模型家族：从 `MODEL.toml`、runtime DSO、bundle 格式到对原始模型的 oracle 比较，能看到模型接入与运行时边界如何配合。仓库虽有代码、CLI、示例、测试和文档，仍为 **Public Preview**；API/模型覆盖可能变化，GPU/TensorRT 环境门槛高，公开 CI 并不等于所有硬件上的精度和性能已得到验证。项目也建议性能优先的 NVIDIA 边缘部署使用 TensorRT Edge-LLM。**建议投入：立即学习（1～3 小时）。先读 Qwen 快速路径和 family/descriptor 校验，再追一项 E2E oracle；有相应 GPU 时才运行完整构建，不宜把项目 README 的“两条命令”理解为零环境成本。**

# 本期最值得关注

1. **MaskRay 的链接器 I/O 分析：深入学习。** 它把热缓存的局部加速、失败时的文件正确性、计量假象和内存峰值放在同一行为链路中，直接提升 C++/编译工具链性能实验的判断质量。先复做 inode/硬链接案例，再检查构建基准有没有跟错进程。
2. **GPT‑6.1 Sol：立即学习。** 对代码和工具任务，先用同一 harness 比较完成率、返工和每成功任务成本，尤其留意 272K 输入阈值；这比摘录跨厂商 benchmark 排名更能指导模型选择。
