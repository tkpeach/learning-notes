本期最有学习价值的是 [Ai2 发布 Olmo-core 3](https://huggingface.co/blog/allenai/olmocore3)：它把大规模 MoE 训练从反复聚集专家权重，改为让专家常驻 GPU、将 token 路由到专家，并公开了端到端吞吐与失效案例。安全方面，[OpenAI 9 月 30 日披露的推理轨迹提取事件](https://openai.com/index/disrupting-a-coordinated-model-distillation-campaign/)与此前独立研究相互印证，提醒采用可在会话间传递的加密推理块时，必须验证其绑定和输出隔离。运行时补漏中，TensorRT Edge-LLM 0.11.0 和 colibri 1.12.1 都有可核验的技术变化；它们的性能数字仍应限定在发布方测试条件内。

# 业界进展

### OpenAI 披露跨会话推理轨迹提取：加密块的可重放性成为安全边界

**质量：A｜重要性：高。** OpenAI 于 9 月 30 日[披露](https://openai.com/index/disrupting-a-coordinated-model-distillation-campaign/)，其调查发现从 7 月开始、试图通过模型交互提取受保护推理的协调行动。官方观察到 7 月 24—25 日超过 4,000 个用户发起约 16,000 次相关请求；进一步调查关联了超过 15,000 个用户的提示模式，并称在 7 月 28 日前完成阻断。**这些是尝试量，不是成功提取量**；OpenAI 还明确表示没有发现加密被破解、数据库失陷或直接读取已存用户对话。对部分行为人的归属是 OpenAI 的判断，官方也承认无法确认全部行为属于同一主体，不能把归属推断当成独立验证的事实。

**机制与独立证据。** 官方举出的路径是：攻击者拿到一个会话中的加密推理块，再诱使另一会话中的模型解码并复述隐藏内容。此前 8 月的[独立研究《Stealing Reasoning Traces from Proprietary LLM APIs》](https://arxiv.org/abs/2608.09867)展示了同类跨会话、跨用户乃至同厂商不同模型可互换的风险，并报告从公开仓库采集的 315,320 个推理块中恢复出个人信息与凭据。论文证明的是研究者构造的攻击路径；OpenAI 公告确认了其系统中相关路径真实存在并已修补，二者不等于公开证明上述大规模行动全部成功。风险也不仅是模型能力蒸馏：隐藏块若进入日志、公开轨迹或下一轮 Agent 上下文，还可能带来数据泄露和不可见提示注入。

**防护与工程判断。** OpenAI 称已关闭持有其他用户加密推理后重放并恢复内容的路径，强化跨用户、工作区、组织和模型家族的隔离，并增加对流式输出泄露推理的检测与拦截；合作部署和工具输出仍在继续加固。这里可迁移的原则是：加密只保护块内容，**不自动保证该块只能在原会话、原权限域和原模型上下文使用**。构建 Agent 轨迹、缓存和回放系统时，应核对来源绑定、跨租户拒绝、压缩/重放路径，以及敏感推理块是否被当普通日志传播。**建议投入：立即学习（1～3 小时）；先读官方事件与论文摘要/威胁模型，再审视自己的会话回放和日志导出边界。**

# 系统与编译器进展

### Olmo-core 3：MoE 训练的关键改动是专家常驻与端到端通信链路

**质量：A｜重要性：高｜Personal Utility：极高。** Ai2 于 10 月 1 日[发布 Olmo-core 3](https://huggingface.co/blog/allenai/olmocore3)，并公开 [Olmo-core 仓库](https://github.com/allenai/Olmo-core)。与此前基于 FSDP、按 microbatch 聚集再重新切分专家权重的实现相比，新系统以 DDP 为基础让专家常驻 GPU，并将 token 路由到相应专家；它把优化焦点从“每次搬专家权重”转向专家并行的通信、缓冲区布局与计算重叠。随后叠加流水线并行、分布式优化器、直接写入专家输入缓冲的 rowwise expert parallelism、GPU 驻留路由元数据和 grouped GEMM。这些机制共同减少权重反复搬运、CPU 等待与许多小 GEMM 的低利用率，不能把结果归因于单个 kernel。

**同口径证据。** 发布方在 8 张 B300 上用 47B 参数 MoE 报告每 GPU 约 52,000 tokens/s，旧 FSDP 路径为 19,400，约 **2.7 倍吞吐**；当专家数从 8 增至 128、每 token 仍选 4 个时，总参数从 4.6B 增至 47B、每 token 活跃参数约 3.2B，吞吐下降不到 5%。这说明该配置下容量增长没有按总参数线性拖累速度，并不说明所有专家负载分布都如此。4 张 B300 的受控测试中，局部采用 MXFP8 相对 BF16 使端到端训练吞吐提高约 21%，峰值活跃显存由 103 GiB 降至 95 GiB；转换成本和低精度数值稳定性仍需随模型与任务验证。

**规模上限与负面结果。** 512 张 B300 上 1.2T 总参数、每 token 活跃 58.36B 的随机路由系统基准，最高观察到 858 TFLOP/s/GPU；2.38T 是短容量测试。两者都**不是完成训练并达到模型质量目标**的证据。报告还记录了负面经验：路由平衡分数可能改善但真实负载更不均衡；按专家较少接收 token 就降低学习率没有带来收益；相同矩阵形状但不同输入值会改变 GPU 时间；计算通信重叠有时反而拖慢全程。这些比单纯峰值数字更能指导实验设计。

**学习与落地。** 学完可明确 MoE 训练中的权重驻留、token all-to-all、优化器状态与计算粒度分别花在哪里，并为自己的训练栈设计可归因的 FSDP/DDP、BF16/MXFP8 对照。仓库提供源码、测试、文档及 `torchrun` 训练入口，但发布数据来自 Ai2 自测，尚缺独立集群复跑；大规模 B300 条件也限制直接复现。**建议投入：深入学习（半天～2 天）。先读发布文的旧/新数据路径与负面实验，再顺着仓库 `src/olmo_core` 的 MoE、并行及训练模块追一次 token 路由与参数更新；可用较小模型先验证正确性和通信占比。**

# GitHub 高价值项目洞察

### [NVIDIA/TensorRT-Edge-LLM 0.11.0](https://github.com/NVIDIA/TensorRT-Edge-LLM/releases/tag/v0.11.0)：部署包、请求语义与并发服务同步补齐（9 月 29 日补报）

**质量：B｜重要性：高｜Evidence Maturity：M1。** 相对已评过的 0.10.1，[0.11.0 发布说明](https://github.com/NVIDIA/TensorRT-Edge-LLM/releases/tag/v0.11.0)确认三条具体增量：为合格的 x86-64/AArch64 平台提供带原生载荷匹配的 wheel；实验性 OpenAI 兼容服务新增可选的**单 rank in-flight batching**；用 C++ 直接渲染模型提供方的 Jinja chat template，并加入 XGrammar 的 JSON/Schema/regex/EBNF 等约束解码。它还扩展 DFlash2、Qwen3.8、Hunyuan 等模型/推测解码路径，并修复特殊 token、KV cache、长上下文接纳及投机接受长度同步问题。对 C++ 推理服务，最值得看的是模型语义从模板到 token 流、以及并发服务的边界，而非模型支持名单长度。仓库有运行时、测试与文档，但 release 没有独立端到端吞吐或并发延迟对照；batching 明确是实验性、单 rank，不应外推为多卡生产服务已成熟。**建议投入：立即学习（1～3 小时）；对照 0.10.1 与 0.11.0 的请求解析、模板渲染和并发调度，用固定模型检查结构化输出、工具调用及批量请求的正确性，再测延迟/吞吐。**

### [JustVugg/colibri 1.12.1](https://github.com/JustVugg/colibri/releases/tag/v1.12.1)：先保证 token 对齐，再谈 MoE 低内存加速（9 月 24 日补报）

**质量：B｜重要性：中｜Evidence Maturity：M1｜Personal Utility：高。** 该版本修复了两处会直接扭曲推理结果或计费判断的 tokenizer 偏差：Qwen 家族在标点后特殊 token、空白切分上与 HF 参考实现不一致，项目方的 2,803 个跨代码、Markdown、中文和日文用例由 757 个一致提升到全部一致；OLMoE 的 ByteLevel 规则也由 1,560/1,708 一致提升至全一致。性能改动则把部分 dense trunk 放入整型 GEMV，并在设备放置前**实测目标显卡**：在测试用 Tesla M10 上，自动放置的部分计算反而慢于 CPU，因此撤回该卡的自动放置并把显存让给专家。另一项 Qwen3.8 测试把 8 线程解码由 0.61 提至 1.42 tok/s、峰值 RSS 由 32.2 降至 28.5 GB；但这来自特定模型、缓存与硬件配置，作者同时报告小样本 perplexity 变化，尚缺独立复现。**建议投入：了解即可（5～20 分钟）；若研究 CPU/GPU/SSD 分层推理，优先读 tokenizer 对照和设备放置回退逻辑，待有可比硬件时再复跑速度与质量。**
