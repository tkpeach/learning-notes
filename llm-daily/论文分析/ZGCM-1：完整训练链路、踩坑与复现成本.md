# ZGCM-1：完整训练链路、踩坑与复现成本

## 一句话判断

信息源的判断**基本正确，但“小规模”容易误导**：ZGCM-1 是 7.39B 稠密模型，从随机初始化经过通用预训练、中训练、SFT、数学 RL，确实比许多只做微调的报告更完整；但通用预训练就用了约 4.19T token、192 张 H100 的配置，不是个人可轻松复制的小实验。主要组件已有先例，价值更集中在将数据、长上下文、数值稳定、工具数据和训练系统接成可追踪的全流程，以及公开阶段代码和资产。论文的“约 4.2 倍效率”和“媲美前沿模型”有明显的实验边界，不能按端到端、同条件结论转述。[论文 §1–5](https://arxiv.org/html/2609.13356v1)、[代码仓库](https://github.com/zgcagi/ZGCM-1)。

## 最值得记住的三点

1. **完整链路是本例的核心学习价值。** 两段 16K 通用预训练（0.99T + 3.20T token）→ 三段 16K/64K/256K 中训练（180B + 240B + 180.51B）→ 256K、19.46B packed token 的 SFT → 已发布模型的数学 GRPO。论文的 mixed RL 是跨数学、代码、指令三个领域的实验计划，并非最终模型使用混合领域 batch；[RL README](https://github.com/zgcagi/ZGCM-1/blob/main/rl/README.md)明确说已发布模型使用数学 RL 阶段。
2. **实际困难多在数据与接口契约。** 词法难度不适合给代码/数学排序，长上下文要渐进扩展并保留短样本；工具调用轨迹要校验 action–observation 配对，SFT 必须检查 chat template、packing 和 loss mask。论文还记录了恢复训练后吞吐从 585 掉到 554 TFLOP/s/GPU，最终通过定期清理 CUDA allocator cache 与垃圾回收恢复。[论文 §3.3、§9.4、§10.3](https://arxiv.org/html/2609.13356v1)。
3. **可复现性强于一般开放权重模型，但并非一键重跑。** [GitHub](https://github.com/zgcagi/ZGCM-1)提供 `pretrain/`、`midtrain/`、`sft/`、`rl/`、`data-process/`；[数据卡](https://huggingface.co/datasets/zgcagi/ZGCM-1-Data)需要接受访问条件，部分上游仅发布索引、还需单独取得数据许可。技术栈、分布式存储、tokenizer、数据清洗和评测环境仍需自己搭建。

## 这次训练具体怎么做

| 环节 | 论文报告的主路径 | 为何这样做 / 需要监控什么 |
|---|---|---|
| 数据准备 | 用 0.3B 代理模型在约 30B token 上筛数据配比；网页、学术/OCR、代码、数学、LaTeX 分源清洗，统一 schema、去重、分片，使用 GLM-5.1 tokenizer；第二段排除第一段内容 | 避免在 7B 上反复试配比；核对每类数据的质量、授权、重复率和 tokenizer 版本。[§3.1.1](https://arxiv.org/html/2609.13356v1) |
| 架构与系统 | 32 层、4096 hidden、32 Q/8 KV heads；27 层 128-token gated SWA + 5 层全局注意力；QK norm、partial RoPE；Megatron、Muon、FP8 delayed scaling、TWEO | 控制长上下文计算与 KV 内存，并抑制 FP8 异常值；记录 loss、梯度/激活、吞吐、通信和 checkpoint 恢复。[§2、§3.1.3](https://arxiv.org/html/2609.13356v1) |
| 通用预训练 | 0.99T token 的词法复杂度课程（仅一般文本排序，代码/数学独立穿插），再 3.20T 全混合；16K，Muon 矩阵参数、Adam 标量参数，LR 2e-4 | 论文表 6：TP/PP/CP/DP = 2/1/1/96，即 192 张 H100；约 585 TFLOP/s/GPU。[预训练 README](https://github.com/zgcagi/ZGCM-1/blob/main/pretrain/README.md) |
| 中训练 | 2.86T 候选池去重后抽 600.51B token；16K→64K→256K，各段持续回放短序列；仍是**全序列 next-token loss**，不是 SFT 的 assistant-only loss。一般 Agent 轨迹转成状态→下一动作示例，加入高质量完整轨迹 | 每步约 12.6M token，batch 从 768/192/48 变化；256K 用 RoPE base 10M、全激活重算。论文比较直接 256K 与先 64K 后 256K，后者末段 loss 1.16 vs 1.19。[§3.2、表 6/9](https://arxiv.org/html/2609.13356v1) |
| SFT | 约 492 万样本，96.46% 通用、3.54% Agent；工具/对话统一到 GLM-5.1 格式，think/no-think 同训；只对 assistant 思考、回复和工具调用计 loss，mask 掉用户和工具观察；发布模型使用 256K、10 epoch、19.46B packed token | 长序列 packing、角色边界、工具观测泄漏都须预检；验证样本是否被静默截断。[§4.1、§10.3](https://arxiv.org/html/2609.13356v1)、[SFT README](https://github.com/zgcagi/ZGCM-1/blob/main/sft/README.md) |
| RL 与评测 | 从初始策略 rollout 筛掉过易题；GRPO 组内比较，数学答案正确性奖励；剔除零方差组，探索 KL/长度惩罚。评测包括通用、数学、搜索、二进制定位、SWE/Terminal | RL rollout 上限 65,536 输出 token、总上下文 98,304；搜索等 Agent 任务还依赖工具、检索 API、判分器和时点。[§4.2、§11](https://arxiv.org/html/2609.13356v1) |

## 论文明确记录的坑与处理

| 坑 | 证据和处理 | 判断 |
|---|---|---|
| 词法复杂度误判代码/数学难度 | 复杂程序排到最易端、简单 NumPy 片段排到最难端；数学亦有相反例子。只排序一般文本，代码/数学独立打乱穿插；剔除乱码异常值。[§9.4](https://arxiv.org/html/2609.13356v1) | 处理方法明确；课程是否普遍有效尚未证明。10B-token 对照中数学 BPB 0.97→0.94，但一般基准 BPB 变差；代码 1.99→0.81 的比较作者称不完全匹配。 |
| 超长上下文直接拉长效果略差、吞吐大降 | 论文的 30B-token 资格实验：先 64K 10B 再 256K 20B，末段 loss 1.16，直接 256K 30B 为 1.19；256K 需要全重算，约 203–204 TFLOP/s/GPU。[§9.1](https://arxiv.org/html/2609.13356v1) | 支持其选择渐进路径，但不能把 30B-token 对照当作全部 600B 中训练的因果消融。 |
| 恢复训练后吞吐缓慢衰退 | 约 80 个匹配 step 从 585 降到 554；释放 overlap buffer 只部分改善；每 100 iter 清 allocator cache 和 GC 后恢复到 585。[§3.3](https://arxiv.org/html/2609.13356v1) | 是具体生产故障和修复记录；对其他 CUDA/TE 版本需重新 profile。 |
| 低质 SFT 与工具协议污染 | 去掉坏角色、重复生成、模板泄漏、无效参数、不配对工具返回；packing 前验证 assistant loss 边界和非空目标。严格筛选在六项平均上 67.78→68.83，单项有升有降。[§4.1、§10.1.1、§10.3](https://arxiv.org/html/2609.13356v1) | 质量筛选收益小而非全面胜利；应以目标任务评估。 |
| 推理数据过重损害直接响应 | 作者调低长推理占比、混入直接响应与指令跟随；历史 checkpoint 比较中 AIME/MBPP+ 增益，但 MMLU -2.60、HumanEval+ -7.32。作者承认此比较并非受控数据消融。[§10.1、§10.4](https://arxiv.org/html/2609.13356v1) | 说明任务间权衡，不能宣称思考训练总能迁移到 no-think。 |
| Agent 能力依赖任务和环境 | 网页搜索、二进制定位表现亮眼，但内部 SWE-bench Verified Mini50 只解决 2/50，Terminal-Bench 2.0 只解决 2/89；论文承认工具格式与反馈噪声脆弱。[§7.2、§11](https://arxiv.org/html/2609.13356v1) | “能做 Agent”不能外推为通用软件工程代理。 |

## 创新性与信息源核验

| 主张 | 已有谱系 / 本文差异 | 证据状态与裁决 |
|---|---|---|
| “完整训练的小模型” | 从零训练 7B，并公开多个阶段资产；这是**开放工程案例**贡献。7B 相对前沿模型小，4.79T 预训练+中训练 token 不小。 | 论文、阶段 README 和模型/数据卡互相印证；“小规模”应限定为参数规模。 |
| SWA 5:1 + gated、256K | SWA、GQA、门控、全局/局部交错均有先例；论文也承认 5:1 已见于 Gemma 3。其贡献是具体配置和 7B/256K 质量-吞吐权衡：256K 对全注意力吞吐 3.94 倍、KV 32→5 GiB。[§2](https://arxiv.org/html/2609.13356v1) | 有局部对照；更偏系统组合与实证优化，而非全新注意力原理。 |
| FP8 + Muon + TWEO 的“4.2 倍” | 三者各有来源。4.2 = 1.4×1.5×1.8×1.1，是 16K 上分项效果相乘的**估算**，不是对同一目标 loss 的端到端平行训练账单。[§3.1.3](https://arxiv.org/html/2609.13356v1) | 支持“有工程效率收益”；不支持“全训练全成本实测节省 4.2 倍”。 |
| MDP Agent 中训练 | 状态-动作重写沿用 agentic continual pretraining 思路；本文把它放进 600B token 的渐进长上下文流程。[§3.2.4](https://arxiv.org/html/2609.13356v1) | 数据组织/配方贡献；未看到足以单独归因 MDP 增益的等预算消融。 |
| AI-native R&D、ACE 评测 | AI agent 参与数据、集群、评测，ACE 有 183 能力/2503 probe；评价可帮助定位失败。[§6、§12–13](https://arxiv.org/html/2609.13356v1) | 过程与工具产物有价值；“大幅压缩迭代周期”缺少公开的人力、时间、对照账本，先视为作者主张。 |
| “媲美前沿模型” | 在 WebWalkerQA 63.09、BrowseComp 19.43、二进制定位 31/50 的特定 harness 有亮点；网页表格混用他方已报告成绩，未统一重跑。网页检索时点、API、摘要器与 judge 会改变结果。[§5、§11、§14](https://arxiv.org/html/2609.13356v1) | 限定任务下有竞争力；不等于综合能力媲美前沿模型。 |

**总体创新判断：** 没有看到可确认的全新基础算法。较有价值的贡献是全流程开放配方、长上下文系统组合、数据治理与失败记录，以及一些有边界的实证观察。“可能没有太多创新”若指算法原理，大致成立；若因此低估完整公开训练案例的工程研究价值，则不准确。

## 复现准备与成本

### 三档目标

| 目标 | 建议做法 | 粗略算力与费用量级 |
|---|---|---|
| **流程复现** | 在 0.1–0.3B 模型上跑 1–30B token，先打通 tokenizer、分源数据、16K 预训练、短中训练、SFT loss mask、简化数学 RL 和同一套评测；保留 checkpoint 与消融 | 30B token、0.3B 参数按 `6ND` 约 5.4e19 FLOP。若实测有效 50–150 TFLOP/s/GPU，约 100–300 GPU·小时；按**假设** $2–5/GPU·小时即 $200–1,500。数据准备、评测与试错可能超过主训练成本。 |
| **机制复现** | 约 1B、50–100B token；各做 SWA/full attention、AdamW/Muon、BF16/FP8、直接/渐进长上下文小对照 | 单次 1B×100B 约 6e20 FLOP；同样 50–150 TFLOP/s/GPU 下约 1,100–3,300 GPU·小时，假设价格约 $2,200–16,500；对照与失败重跑另计。 |
| **原尺度重训** | 重建全部许可数据、192×H100 集群、分布式共享存储与多阶段 checkpoint，再复跑 SFT/RL、检索和执行环境 | 仅 4.19T 通用预训练按 `6×7.39B×4.19T / 585 TFLOP/s` 约 **8.8 万 GPU·小时**，192 卡理想净训练约 19 天；以假设 $2–5/GPU·小时仅此段约 **$18–44 万**。600B 中训练、长序列低吞吐、SFT/RL、数据生产、消融、停机和人员均额外计费；不能把该数称为完整项目报价。 |

`6ND` 是稠密 Transformer 的粗略训练 FLOP 估算，忽略注意力的长序列附加开销、激活重算、通信、数据管线、推理 rollout 与故障恢复。上述单价只是预算情景，不是 2026-09-17 的云报价；下单前应以实际区域、租期、网络/存储及实测 token/s 重算。优先验证最小模型的正确性与吞吐，再扩大规模。

### 最小复现验收清单

1. 固定代码版本、tokenizer/hash、数据许可、训练与验证清单；留出并去污评测集。特别核实 [数据卡的 index-only 与上游单独访问要求](https://huggingface.co/datasets/zgcagi/ZGCM-1-Data)。
2. 先在小模型上验证：跨阶段 checkpoint 接续、分布式等价、FP8 数值无异常、Muon/Adam 参数分组、SWA 掩码和 KV cache、长序列 loss、SFT assistant-only mask、工具调用与返回配对。
3. 每个关键主张只做一个匹配对照：同 token/硬件/数据比 SWA 与全注意力，同有效 batch/目标 loss 比 Muon+FP8 与 BF16/AdamW，同 token 预算比渐进与直接扩窗；报告速度、loss、质量及误差区间。
4. Agent 评测锁定工具、搜索索引日期、抽取器、judge、超时和重试；同时报告无工具、固定检索结果和端到端在线结果。

## 两个会改变结论的争议

### 争议一：它真的“完全开放、可直接复现”吗？

初始主张：论文称模型、代码、数据、日志均开放。反方质疑：数据卡要求登录接受条件，若干上游只给定位索引，复现者必须另取授权。关键证据：[项目仓库](https://github.com/zgcagi/ZGCM-1)存在各阶段工作流；[数据卡](https://huggingface.co/datasets/zgcagi/ZGCM-1-Data)说明访问门槛和 index-only 记录。回应：公开程度确实高于一般只给权重的项目，但“完全开放”不等于全量训练文本无条件可下载。**裁决：部分支持。** 这使原尺度重训首先成为数据许可与重建项目，而非单纯算力项目。

### 争议二：效率和前沿能力能否支撑大额重训？

初始主张：约 4.2 倍 time-to-loss、在若干 Agent 基准接近大模型。反方质疑：效率数字为跨实验分项相乘；网页 Agent 比较并非统一重跑，泛化到 SWE/Terminal 的结果很弱。关键证据：[论文 §3.1.3、§5、§11、§14](https://arxiv.org/html/2609.13356v1)及 2/50、2/89 的内部诊断。回应：局部配置优化与目标场景表现有直接证据，但整体成本和通用 Agent 能力缺少相同条件验证。**裁决：部分支持。** 更合理的下一步是先做小规模机制对照，而非按论文的 4.2 倍去预算完整重训。

## 尚未回答的问题与下一步

- 论文未给完整训练的实际 GPU·小时、设备租价、数据处理/教师模型调用和失败实验账单；也未充分隔离 MDP、TWEO、AI agent 工作流各自对最终质量的贡献。
- 需核对所有数据分片是否能按公开索引与上游许可重建到相同 hash，及发布的 W&B/评测原始输出是否覆盖最终每一项结论。
- 建议先复现 **0.3B 代理实验 + 两个匹配机制对照**：课程排序（一般文本 vs 随机）与长上下文渐进扩窗；以固定验证 BPB、长文本检索、短上下文回归和训练吞吐作为停/继续标准。再决定是否扩大到 1B。
